# skill-prior-art

新規スキルを書き始める前の調査ゲート。出力は**スキルではなく調査レポート1枚**で、
最後に「採用 / ベンダー公式 / 派生 / 自作」のどれかを根拠つきで宣言する。

## 鉄則

**調査レポートが `check_report.py` を通るまで、SKILL.md を1行も書かない。**

言い訳と、それが成り立たない理由:

| 言い訳 | 反論 |
|---|---|
| 「ニッチだから無いはず」 | skills.sh は100万件超。ニッチほど誰かが既に踏んでいる |
| 「日本語の要件だから海外には無い」 | 骨格は同じで日本語化だけが差分、はよくある。それは自作ではなく**派生** |
| 「探すより書いた方が速い」 | 速いのは初版だけ。保守と、公式が同じものを出した時の合流コストが乗る |
| 「前に調べたときは無かった」 | エコシステムは週単位で動く。前回の記憶は証拠にならない |
| 「もう書き始めてしまった」 | 書いた分は捨てなくていい。調査してから合流先を決めればいい |

例外なし。ユーザーが明示的に「調査はいらない、そのまま作って」と言った場合のみ、
その旨をレポートに記録して skill-creator に進む。

## 記憶で答えない

スター数・インストール数・「そのリポジトリに何があるか」を**記憶から書かない**。
学習時点の値は必ずずれているうえ、集計サイトごとに数字が食い違う。

- 数値と存在は、**今日取得した画面かコマンド出力**だけを根拠にする
- レポートの各主張には取得元URLを添える。添えられないものは書かない
- 「無い」と書くときも、**実行したクエリを残す**。クエリの無い「該当なし」は未調査と同じ

## 手順

### Step 0 — 何を探すのか1文にする

「何をする / いつ発動する / どのサービス・技術に触る」を1文で書く。
ここから検索語を英語3〜5個 + 日本語1〜2個作る。英語が主戦場なので英語を先に作る。

例: 「PR作成時にブランチ名からチケット番号を拾い、diffを分類してPR本文を書く」
→ `pull request description`, `pr template`, `conventional pr`, `git diff summarize`

### Step 1 — 6つの層を上から順に潰す

**上ほど信頼が高い。上で見つかったら下は軽く流してよいが、T0〜T2は必ず全部見る。**

| 層 | 探す場所 | なぜこの順か |
|---|---|---|
| T0 | 手元（自分のリポジトリ / `~/.claude/skills` / plugins cache） | 最も多い重複はここ。自分が半年前に作ったものを忘れている |
| T1 | Anthropic公式（`anthropics/skills`、内蔵スキル、`claude-plugins-official`） | 公式は本体の挙動に追随して更新される。自作は追随しない |
| T2 | **作業対象サービスのベンダー公式** | GitHub操作なら GitHub、Supabase操作なら Supabase。仕様変更に一次情報で追随する |
| T3 | Claudeマーケットプレイス（`/plugin` Discover、claude.com/plugins） | 審査があり、`/plugin update` で更新が届く |
| T4 | skills.sh レジストリ | 網羅性は最大。ただし**無審査**なので中身を読むまで信用しない |
| T5 | 著名企業・著名個人の公開スキル | 保守が続く見込みが立つ |

**T2は最も見落とされ、最も効く。** 既存サービス上の作業をスキル化しようとしているなら、
そのサービス自身が公式スキルを出していないかを必ず確認する。
具体的なコマンドと調べ先の一覧は `references/sources.md` を読むこと。

### Step 2 — 候補を読む

名前と説明文だけで判断しない。SKILL.md 本文まで読んで、次を書き出す。

- **できること** — 要件のうち何を満たすか
- **足りないこと** — 何を満たさないか（ここが空欄なら、それは自作の理由が無いということ）
- **提供元と保守状況** — 誰が出しているか、最終更新はいつか
- **監査結果** — 外部スキルを採用・派生する場合は必須（`references/sources.md` 参照）

外部スキルを**勝手にインストールしない**。レポートに載せて、ユーザーが選ぶ。

### Step 3 — 4択で結論を出す

| 結論 | 意味 | 次の一手 |
|---|---|---|
| `adopt` | そのまま使える | インストールを提案して終了。作らない |
| `vendor` | 取り込んで薄く差分を当てる | `bash ${CLAUDE_SKILL_DIR}/scripts/vendor.sh <owner/repo> <パス> --dest <取り込み先>` でSHA固定して取り込み、レビュー |
| `derive` | 骨格を借りて作り直す | 借用元を明記して skill-creator へ |
| `build-new` | 該当なし | **既存で満たせない点を列挙してから** skill-creator へ |

`derive` と `build-new` は「既存で満たせない点」を最低1つ書けないと選べない。
書けないなら答えは `adopt` か `vendor`。

### Step 4 — レポートを書いて検証する

`templates/report.md` の形式で書き、機械検証を通す。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/check_report.py <レポートのパス>
```

exit 2 で落ちたら直す。調査層の抜け・出典の無い数値・空欄の結論はここで止まる。

### Step 5 — 引き渡す

結論をユーザーに1段落で伝え、`build-new` / `derive` なら skill-creator に進む。
レポートはリポジトリに残す。次に似たスキルを作るとき、この調査が再利用できる。

## 参照ファイル

- `references/sources.md` — 各層の具体的な調べ先、コマンド、既知のベンダー公式スキル一覧
- `templates/report.md` — レポートの雛形
- `scripts/search_local.sh` — T0（手元）の重複を機械的に洗い出す
- `scripts/check_report.py` — レポートの機械検証。exit 2 で落とす
- `scripts/vendor.sh` — 外部スキルをSHA固定で取り込む。`vendor` を選んだときだけ使う

## このスキル自体の先行事例

同種のスキルは既にある。差分を理解した上で使うこと。

- `vercel-labs/skills@find-skills` — レジストリ最多インストール。**使うスキルを探す**用途で、
  作者自身が「スキルを書く側なら skill-creator へ」「人気順であって審査ではない」と書いている
- `affaan-m/ecc@skill-scout` — 最も近い。ローカル→GitHub→Webの順で探して3択を出す。
  ただし信頼度の階層が無く、ベンダー公式を見に行く手順が無く、skills.sh を使わない

このスキルの差分は、**信頼度で層を切って上から潰すこと**と、**T2（作業対象サービスの
ベンダー公式）を必須にしたこと**、そして**結論を機械検証すること**の3点。
