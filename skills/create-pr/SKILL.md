# create-pr

作業ブランチに積んだコミットを、そのリポジトリの書式に沿った Pull Request にして、
**承認を得てから** 作成する。

## 担当範囲

開発の流れのうち、**4番目だけ**を担当する。

1. 作業ブランチを切る → `create-branch`
2. 開発作業をする
3. 時折コミットする → `git-commit`
4. **作業ブランチの内容を PR にまとめる** ← ここ

このスキルはコミットを作らない。ブランチも切らない。3までが済んでいる状態を入力として受け取る。

**`main` → `release` のような本番リリースの PR は `release-pr` の担当。** base が本番ブランチで
head が dev ブランチそのものなら、こちらではなくあちらを使う。差分は全部レビュー・CI 済みで、
本文の価値が「何をしたか」ではなく「マージ後に本番が動く前提が揃っているか」に移るため、
手順が別物になる。

## 絶対原則

- **本文を提示して承認を得るまで作成しない。** 提示（手順6）と実行（手順7）は必ず別ターン。
  手順6を出したらターンを終了して返信を待つ。PR を作るとレビュワーに通知が飛び、CI が回り、
  取り消しても痕跡は消えない。「PR作って」は通常のトリガーであって確認スキップ指示ではない。
- **差分は `origin/<base>...HEAD` で取る。`git diff HEAD` を使わない。** 後者は未コミットの
  変更しか見えない。フェーズごとにコミットしてきた後は作業ツリーがクリーンなので、
  `git diff HEAD` はほぼ空になり、本文の材料が消える。ここを間違えると、大きなタスクの PR が
  「最後に触ったファイルだけ」の説明になる。
- **リポジトリのテンプレートが最優先。** `.github/PULL_REQUEST_TEMPLATE.md` があれば、
  下の「テンプレート」章より必ずそちらを使う（手順2）。自前のテンプレートを押し付けない。
- **コミットも push も勝手にしない。** 未コミットの変更が残っていたら手順4で止まる。
  push は手順6で承認を取ってから手順7で行う。
- **やっていない検証を「確認済み」と書かない。** 「確認」セクションに書けるのは、実際に
  実行したコマンドとその出力だけ。回していないテストの名前を並べると、レビュワーは
  通ったものとして読む。実行していなければ、その旨を書くか節ごと省く。
- **本文はコミットメッセージではなく差分を正とする。** メッセージは書いた時点の意図であって、
  差分と食い違うことがある。「集約した」と書いてあるのに削除された重複が差分に無い、
  「挙動は変えない」と書いてあるのに受理範囲が変わっている、などは珍しくない。メッセージを
  そのまま本文に写すと、レビュワーは差分ではなく作者の意図を読んでしまい、食い違いが
  レビューをすり抜ける。裏が取れた事実だけを本文に書き、食い違い自体は手順6で伝える。
- 機微情報（トークン・認証情報・個人情報・本番の内部URL）を本文に含めない。

## 手順

### 1. ブランチとベースを確定する

```bash
git rev-parse --abbrev-ref HEAD          # 作業ブランチ
git remote get-url origin                # ホスト判定と owner/repo
git status --short                       # 未コミットの変更（手順4で使う）
```

- `github.com` → `gh` で作成できる（手順2へ）
- **それ以外（`bitbucket.org` など）→ `gh` は使えない。** 本文までは同じ手順で作り、
  手順8のフォールバックで出力する。`gh` を使う調査（手順2の一部・手順5）は飛ばす。

`owner/repo` は remote URL から取り出し、以降の `gh` コマンドで **必ず `-R owner/repo` を
明示する**（別リポジトリのディレクトリから呼ばれても取り違えないため）。

**ベースブランチは既定に任せず、自分で確定させる。**

```bash
gh repo view <owner/repo> --json defaultBranchRef --jq .defaultBranchRef.name
gh pr list -R <owner/repo> --state merged --limit 10 --json baseRefName --jq '.[].baseRefName' | sort | uniq -c
```

2つ目が運用の実態を示す。**既定ブランチと、実際に PR が向いている先は一致しないことがある**
（既定が `main` でも全 PR が `develop` 行き、など）。食い違ったら多数派を採り、その旨を
手順6で一言添える。`gh pr create` に `--base` を渡さないと既定ブランチが使われるので、
確定した値を必ず明示する。

### 2. リポジトリの方針とテンプレートを確認する

```bash
cat .github/PULL_REQUEST_TEMPLATE.md 2>/dev/null || ls .github/PULL_REQUEST_TEMPLATE/ 2>/dev/null
grep -niE "pull request|\bPR\b|マージ|レビュー" CLAUDE.md README.md .github/CONTRIBUTING.md 2>/dev/null | head -20
```

**テンプレートがあれば、その見出しをそのまま使い、順序も変えない。** 「変えない」には
**`##` の節を足さないこと**も含む。伝えたいことがテンプレートに置き場を持たないときは、
既存セクションの配下に `###` で収める（テンプレート章の冒頭を参照）。さらに
**HTML コメント（`<!-- -->`）の中身を必ず読む。** 運用ルールがそこに書かれていることが多い。

> 例: 「PRタイトル命名ルール: `<type>: Title`」「レビュワーは自動ルーティング」
> 「マージは Squash」「@fe-reviewers の承認が必要」

タイトル規則が書かれていたら従う。レビュワー指定やマージ方法の指示は、本文には書かず
手順6でユーザーに伝える（このスキルはマージしない）。

`CLAUDE.md` が PR 作成を制限していることもある。制限があれば **作成せずユーザーに提示して
指示を仰ぐ。** ユーザーが明示的に依頼していても、方針と食い違う旨は必ず一言伝えてから進める。

### 3. 変更を読む

`<base>` は手順1で確定した値。**コミット履歴が本文の骨格になる。**

```bash
git log origin/<base>..HEAD --pretty=format:'%h %s%n%b'   # コミット単位の意図
git diff --stat origin/<base>...HEAD                      # 変更の広がり
git diff origin/<base>...HEAD                             # 実際の差分
```

コミット（`..`）と差分（`...`）でドットの数が違う。差分は3つ。マージベースからの差分になり、
PR 画面に出るものと一致する。

ブランチが未 push でも `origin/<base>` は存在するので、この3つはそのまま使える。
`origin/<base>` が無ければ `git fetch origin <base>` を先に行う。

**読む順序が結果を決める。** コミットメッセージを先に読む。フェーズごとにコミットされて
いれば、各コミットが1つのテーマになっているので、それが「変更内容」の見出しになる。
diff を先に読むとファイル単位の羅列になり、なぜその変更をしたのかが落ちる。

**そのうえで、メッセージを差分で検証する。** 骨格には使うが、内容の裏は差分で取る。
次の2つは特に頻発する。

- **「集約した」「移動した」「重複を消した」** → 削除された側が差分にあるか。無ければ
  それは集約ではなく新規追加。元があったかは元のファイルを直接見て確かめる。

  ```bash
  git show origin/<base>:<path>     # 変更前のファイル
  git grep -n "<移したはずの処理>" origin/<base>   # base 側に本当にあったか
  ```

- **「挙動は変えない」「リファクタリングのみ」** → 条件式・正規表現・デフォルト値の受理範囲が
  変わっていないか。テストが追加されているなら、**そのテストが何を弾くようになったかを読む。**
  弾くようになった値があるなら、それは挙動変更。

裏が取れなかった主張は本文に書かない。「機械的な変換だから挙動は変わらない」は、
確かめたときにだけ書ける。確かめられなかったら、そう書いて手順6の確認事項に回す。

diff だけからは分からないもの（なぜこの設計にしたか、何を捨てたか、どこで詰まったか）は、
**このセッションの文脈から拾う。** 大きなタスクの PR で本当に価値があるのはここで、
diff を読めば分かることではない。

### 4. 未コミットの変更を確認する

手順1の `git status --short` に何か出ていたら、**そのまま進めない。**

未コミットの変更は PR に含まれない。含まれないまま「この PR の変更内容」を書くと、
本文と実際の差分がずれる。かといってこのスキルはコミットを作らない。

ユーザーに次を伝えて指示を仰ぐ。

- 何が未コミットで残っているか（ファイル名）
- それを含めるなら `git-commit` でコミットしてから、もう一度 PR を作ること
- 含めないなら、そのまま進めてよいか

生成物やログのような、明らかに PR と無関係なファイルだけなら、その旨を添えて進めてよい。

### 5. タイトルを決める

手順2でタイトル規則が見つかっていればそれに従う。無ければ既存 PR に倣う。

```bash
gh pr list -R <owner/repo> --state merged --limit 10 --json title --jq '.[].title'
```

`feat:` `fix:` のような接頭辞が並んでいれば付ける。付いていなければ付けない。
言語（日本語/英語）も揃える。

**内容**: 何が変わるかを、それ単体で読んで分かる具体さで書く。1行で完結させ、末尾に句点を
付けない。ブランチ名にチケット番号が入っていて、既存 PR も付けているなら踏襲する
（`[ABC-123] ...` など）。既存 PR が付けていないなら付けない。

- 良い: `refactor: PR 作成を公式 commit-commands に委譲し、create-issue を汎用化する`
- 悪い: `修正` / `ブランチの変更をまとめました` / `WIP`

### 6. 提示して承認を得る（ハードストップ）

次を提示して、**ターンを終了し承認を待つ**。

- 作成先（`owner/repo`）と **base ← head** のブランチ名
- タイトル
- 本文の全文
- **未 push なら、その旨と push してよいかの確認**（PR 作成に必要）
- 手順1で base の食い違いを見つけていれば、どちらを採ったか
- 手順2で見つけた運用ルール（レビュワー指定、Squash マージなど）
- draft にするか（既定は通常の PR。draft が欲しいと言われたときだけ `--draft`）
- **裏が取れず空欄にした項目**（黙って省略しない）

### 7. 作成する（承認後の別ターン）

未 push なら先に push する。

```bash
git push -u origin <作業ブランチ>
```

本文を一時ファイルへ書き出してから作成する（本文の記号がシェルに壊されないよう、
`--body` ではなく `--body-file` を使う）。

```bash
gh pr create -R <owner/repo> \
  --base <base> \
  --head <作業ブランチ> \
  --title "<タイトル>" \
  --body-file /tmp/pr_body.md
```

- `--base` は必ず渡す。省くとリポジトリの既定ブランチになる。
- draft を頼まれていれば `--draft` を足す。
- 作成後、返ってきた URL をユーザーに返す。
- **CI があるなら結果も見る。** 落ちていたら伝える。緑になるまで PR を放置しない。

```bash
gh pr checks <番号> -R <owner/repo>
```

### 8. フォールバック（GitHub 以外 / `gh` 未認証・未インストール）

**Bitbucket などのリポジトリでは `gh` は使えない。** 作成を諦めるのではなく、生成した
タイトルと本文を Markdown のまま出力し、ユーザーがそのまま貼れる形で渡す。base と head の
ブランチ名も添える。

GitLab で `glab` が入っていれば `glab mr create` が使える。無ければ同じく Markdown を出力する。

`gh` が未認証の場合も同じく Markdown を出力し、`gh auth login` が要る旨を伝える。

## テンプレート

**リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` があれば、この章は使わない。**
無いリポジトリでの受け皿として、変更の種類で3つ用意している。

どれも、**該当しないセクションは丸ごと省く。** 空の見出しだけ残さない。
1つの PR に複数の性質が混ざっているときは主たるものを選び、足りない節だけ他から借りる。

**リポジトリのテンプレートを使うときは、この章の節を `##` で足さない。** テンプレートの h2 は
レビュー運用に紐づいていることがあり（「動作確認にスクショを貼る」「この節を見て承認する」など）、
増やすと本文の形が他の PR と揃わなくなる。

とはいえ「挙動が変わる点」を黙って落とすと事故になる。テンプレートに置き場が無いときは、
**既存セクションの配下に `###` で収める。** 「修正内容」があればそこ、無ければ内容が最も近い
節の下。見出しを増やさずに、読まれる位置に置くのが狙い。

### リファクタリング

````markdown
## 概要

（何をどう変えたか1〜3文）

## 背景

（なぜ必要だったか。diff からは分からないので、ここが本文の価値になる）

## 変更内容

### （フェーズ = コミット単位）

-

## 挙動が変わる点

（**混ざっていたら、独立した節で先に書く。** 隠すと後で事故になる。無ければこの節ごと省く）

- （何がどう変わるか。受理範囲が狭まった、シグネチャが変わった、API の形が変わった、など）
- （それによって誰が影響を受けるか。既存データ、外部の呼び出し元、サーバー側の同時対応）

## 挙動が変わらない根拠

（上の節に挙げた点を**除いた**部分について、次のどれで担保したかを書く）

- 既存のテストが通っている（コマンドと出力）
- 変換が機械的である（同じ置換をN箇所に適用した、など）
- 差分の性質上、挙動に触れない（型定義のみ、ファイル移動のみ、など）

**確かめられなかったものをここに書かない。** 「集約しただけ」と書く前に、削除された側が
差分にあるかを見る（手順3）。無ければ機械的な変換ではないので、この節ではなく確認事項に回す。

## 確認

```
（型チェック・Lint・テスト・ビルドの実行結果）
```

## 残課題
````

## 初めて触るリポジトリで最初に見ること

**リポジトリ固有の値をこのスキルに書き溜めない。** ベースブランチ・テンプレート・タイトル
規則・CI の構成はリポジトリごとに違い、時間でも変わる。毎回コマンドの出力を正とする。

```bash
git remote get-url origin                                          # ホストと owner/repo
gh repo view <owner/repo> --json defaultBranchRef --jq .defaultBranchRef.name
gh pr list -R <owner/repo> --state merged --limit 10 --json title,baseRefName   # 規則と実際の base
cat .github/PULL_REQUEST_TEMPLATE.md 2>/dev/null                   # テンプレートの有無
```

判断の目安。

- 既定ブランチと merged PR の base が食い違う → **PR の base は後者に合わせる**
- タイトルに `feat:` 等が並んでいる → 踏襲する。無ければ付けない
- `.github/PULL_REQUEST_TEMPLATE.md` がある → 上のテンプレート章より優先する
- テンプレートの HTML コメントに運用ルールがある → 読んで手順6で伝える
- remote が `github.com` 以外 → 手順8のフォールバックへ

リポジトリごとの事情（レビュー体制、マージ方法、PR を作ってよいタイミング）は、
このスキルではなく **そのリポジトリの `CLAUDE.md`** に書く。そちらは手順2で必ず読む。
