# doc-brief

会話やコードの中にある情報を、**他人が読む1枚の .md** に落とす。

書くこと自体ではなく、**書かないことを決めること**を引き受ける。セッションの中には、
調べた事実・試して駄目だった案・途中で変えた前提・最終的な結論が混ざって積み上がっている。
そのまま吐き出すと、書いた本人には完璧に読めるのに、読者には「何を知ってほしいのか
分からない長文」になる。この落差が事故の正体で、長さはその症状にすぎない。

**軽く回すこと自体が要件。** 重い工程は「あとでドキュメントにしよう」を遠ざけるので、
既定では §0 → §1 → §2 → §3 を一息で通す。参照ファイルは判断に詰まったときだけ開く。

## 0. 読者と物差しを決める

本文を1文字も書く前に、2つを書き出す。ここを外すと以降が全部間違った方向に最適化される。

1. **誰が読むか** — その人がこの領域について既に何を知っているかまで。
   読者の既知を書けると、前提の再説明をまるごと落とせる
2. **読んだ後に何が起きてほしいか** — 判断する／作業を再現する／状況を把握する のどれか。
   これが §2 の唯一の物差しになる

依頼が曖昧で埋まらないなら、想像せずユーザーに聞く。**応答を待てない実行（バッチ・自動化・
相手が手を離れている）では止まらない。** 素材から最も確からしい読者と目的を推定し、
その仮定を文書末尾の「まだ確認していないこと」に書き出す。黙って仮定するのが最悪で、
書いてあれば読者が違和感に気づける。

## 1. ヘッダと骨格

### 定型ヘッダ — 省略しない

```markdown
# タイトル

作成日: YYYY-MM-DD

最終更新日: YYYY-MM-DD

作成者: <人名> with <実行中のモデル名>
```

日付は今日の実日付を入れる（`YYYY-MM-DD` の残骸を納品しない）。既存ファイルの更新では
**最終更新日だけ**を今日にし、作成日は動かさない。この2つが揃って初めて「いつの情報か」と
「どれだけ放置されたか」が伝わる。モデル名は実行中のもの。分からなければ `Claude` とだけ書く。

### タイトルと見出しは結論を書く

これが読み手に最も効く一手で、しかも最も忘れられる。

- タイトル: `認証基盤の調査` ではなく `認証基盤は Auth0 ではなく Clerk を採用する`。
  一覧に並んだとき、中身を開かずに済むかが基準
- 見出し: `## 原因` ではなく `## なぜ壊れたか — 単独では無害な4つが重なった`。
  `## 外部サービス` ではなく `## 知らずに踏むと原因にたどり着けない4か所`

**見出しだけを上から読んで話が通るか**を、本文に入る前に確認する。通らなければ、
それは構成の問題であって書き方の問題ではない。

文書タイプ別の骨格（調査レポート／手順書／設計メモ／障害報告／引き継ぎ）は
`assets/template.md`。骨格の並び順は出発点であって、§0 の物差しと衝突したら物差しが勝つ。

### 上限を決める

先に上限を決める。これが次の判断の基準になる。

| 上限 | 読了時間 | 向く文書 |
|---|---|---|
| 1,200字 | 2〜3分 | 作業メモ、チャットに貼る報告、短い手順 |
| 2,500字 | 5分 | 標準的な社内ドキュメント、引き継ぎ、障害報告 |
| 5,000字 | 10分 | 調査レポート、設計メモ、まとまったガイド（既定） |

既定は5,000字。`count.py --limit N`（→ §3）で指定する。上限を上げる前に、
分割で済まないかを先に考える。読者が10分で読み切れない文書は、読まれないか、
斜め読みされて誤読される。長さは品質ではない。

### 素材が上限を超えているときだけ、字数を配る

素材がファイルなら、まず素材そのものに count.py（→ §3）を当てる。

- **素材の地の文が上限以下** — 要約するのだから超過しようがない。配分は省く。
  ここで字数を振るのは、制約として何も効いていない儀式になる
- **素材が上限を超えている** — 見出しに字数を配ってから本文に入る
  （`## 手順 1,200字` のように）。書いてから削るのは苦痛で、しかも削り方を間違える——
  たいてい、手間をかけた節が惜しくて残り、一番大事な結論が薄いまま出る。
  配分の合計が上限を超えるなら、**書く前に**分割を決める（→ §3）

素材が会話の中にしかないなら、当てるファイルが無いので勘で判断してよい。
迷ったら配分する側に倒す。

## 2. 何を落とすか

§0 で決めた「読んだ後に何が起きてほしいか」に**寄与しない情報を落とす**。

> この段落は、読者の判断や作業を変えるか。
> 変えないなら、それは書いた本人にしか価値がない情報である。

**落とす** — 採らなかった案の検討経緯、試行錯誤の順序、自分が理解するために必要だった
前提の再説明、ツールやサービスの一般的な説明、「網羅したから」だけの理由の列挙。

**残す** — 読者が再現・検証するのに要る固有名詞・パス・コマンド・数値、判断の分岐点と
その採否理由、既知の落とし穴、次の一手、**調べていない範囲の開示**。
最後の項目が抜けると、読者は書かれていないことを「確認済み」と読む。削りすぎの中で
もっとも高くつく。

落としたものは黙って消さず、2通りで扱い分ける。

- **畳む（既定）** — 本文に結論と一行の理由だけ残す。「A は B の制約で使えなかった」。
  ほとんどの経緯はこれで足りる
- **付録へ逃がす** — 別ファイルにして本文から一行でリンクする。**畳むと失われるときだけ。**
  生ログ全文、全件の一覧、後から参照される調査記録がこれに当たる

どちらにせよ、検討したという事実は本文に残す。消したのか、そもそも検討していないのかが
読者に区別できないと、同じ調査をやり直させることになる。

経緯・表・網羅・コード量・前提の説明量で判断に詰まったら `references/selection.md` を開く。
迷っていないなら開かなくていい。

## 3. 数える

書き終えたら一度だけ機械で数える。目分量で判断しない。

**この SKILL.md を読み込んだディレクトリ**の `scripts/count.py` を呼ぶ。読み込んだパスは
分かっているはずなので、そこから組み立てる。

```bash
python3 <このSKILL.mdのあるディレクトリ>/scripts/count.py <file>
```

配布経路によってパスが変わる（`~/.claude/skills/doc-brief/` のこともあれば、プラグインの
キャッシュ配下のこともある）。**`${CLAUDE_SKILL_DIR}` は設定されていないことがあるので
使わない** — 空文字に展開されて `python3 /scripts/count.py` になり、黙って落ちる。
パスを見失ったら探す。

```bash
find ~/.claude -path '*/doc-brief/scripts/count.py' 2>/dev/null | head -1
```

見出しごとの内訳と合計が出て、上限超過は exit 2 で落ちる（既定5,000字、`--limit` で変更）。

**数えるのは地の文だけ。** コードブロック・表・ヘッダのメタ行・リンクのURLは除外する。
これらを数に含めると、読者が実際に必要としているコマンドや設定値を削る圧力がかかり、
字数を守った結果として使えない文書ができあがる。裏を返すと**コードと表の水増しは
字数に出ない**ので、そこは自分で見る。

**超過したら、削る前に上から試す。** 削ると情報が失われるが、分割なら失われない。

1. **付録に逃がす** — 経緯・生ログ・全件一覧を別ファイルへ。本文からリンクする
2. **読者を分ける** — 「実装者向けの手順」と「意思決定者向けの要約」が混ざって
   膨らんでいることが多い。分ければ両方とも短く、かつ読みやすくなる
3. **前提を落とす** — §0 の「読者が既に知っていること」に戻る
4. **畳む** — ここまでで収まらなければ、はじめて圧縮する。削るのは説明の重複であって
   事実ではない。事実・数値・固有名詞を削り始めたら 1 に戻る合図

内訳を見て**一つの節が全体の半分を超えていたら、構成の失敗**を疑う。たいてい、
そこは本文ではなく付録に属する。

アウトラインのメモや下書きを作ったなら、ここで消す。残すのは完成した .md と付録だけ。
付録にも本体と同じ定型ヘッダを付け、タイトルに「〈本体名〉の付録」と分かる語を入れる。

## 4. 仕上げ

最後に自分で通読して、次を見る。ここまでの工程が効いていれば、どれも数秒で済む。

- 結論が冒頭にあるか。見出しだけ読んで話が通るか
- 一文が長すぎないか（80字を超えたら切れないか疑う）
- 箇条書きが「本当に並列なもの」だけか。説明は地の文で書けているか
- 全部の節が同じ厚みになっていないか。重要な節が厚いか
- ヘッダの日付が実日付か

**対外文書・経営向け・公開物のように、日本語の質が失敗コストに直結するものだけ**、
Skill ツールで `natural-japanese:natural-japanese` を `quick <file>` を引数に呼ぶ
（プラグイン由来なので名前空間が付く）。禁止語・翻訳調・読解負荷を機械検出して直せる。

社内文書に毎回これを回すと、削って整えた文章をさらに磨き直すことになり、
このスキルが軽く回るという前提が崩れる。**迷ったら呼ばない。**

順序は動かさない。**削る・分けるが先、磨くが後。** 文体を整えてから削ると、
磨いた文章を捨てることになる。

## 参照ファイル

- `assets/template.md` — 定型ヘッダと、文書タイプ別の骨格
- `references/selection.md` — 取捨選択で詰まったときだけ。経緯・表・網羅・コード量・前提
- `scripts/count.py` — 地の文の字数を見出し単位で数える。上限超過で exit 2
