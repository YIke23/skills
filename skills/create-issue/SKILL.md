# create-issue

調査した内容を、そのリポジトリの書式に沿った Issue にして、**承認を得てから** 起票する。

## 絶対原則

- **本文を提示して承認を得るまで作成しない。** 提示（手順7）と実行（手順8）は必ず別ターン。
  手順7を出したらターンを終了して返信を待つ。Issue は外部に出る成果物で、取り消しても
  通知は消えない。「issue立てて」は通常のトリガーであって確認スキップ指示ではない。
- **プロジェクト側の方針が優先。** リポジトリの `CLAUDE.md` が Issue の作成を禁じている
  ことがある（手順2）。禁止されていればユーザーに伝えて指示を仰ぐ。
- **推測で本文を書かない。** ファイル名・行番号・エラーメッセージ・再現手順は、実際に
  コードを読むか実行して確かめたものだけ書く。裏が取れないものは書かず、空欄で残す。
- **既存のラベルだけ使う。新しいラベルを作らない**（手順6）。
- 機微情報（トークン・認証情報・個人情報・本番の内部URL）を本文に含めない。

## 手順

### 1. リポジトリとホストを判定

```bash
git rev-parse --show-toplevel     # リポジトリルート
git remote get-url origin         # ホスト判定
```

- `github.com` → `gh` CLI で起票できる（手順2へ）
- **それ以外（`bitbucket.org` など）→ `gh` は使えない。** 本文までは同じ手順で作り、
  手順9のフォールバックで出力する。手順4・6（`gh` を使う調査）は飛ばす。

`owner/repo` は remote URL から取り出し、以降の `gh` コマンドで **必ず `-R owner/repo`
を明示する**（別リポジトリのディレクトリから呼ばれても取り違えないため）。

### 2. プロジェクトの方針を確認

リポジトリルートで次を確認する。ここを飛ばさない。

```bash
grep -niE "issue|起票" CLAUDE.md README.md .github/CONTRIBUTING.md 2>/dev/null | head -20
ls .github/ISSUE_TEMPLATE 2>/dev/null                 # テンプレートがあればそれに従う
```

Issue 作成を制限する記述があれば、**起票せずユーザーに提示して指示を仰ぐ。**
ユーザーが明示的に依頼している場合でも、方針と食い違う旨は必ず一言伝えてから進める。

> 例: 「公開リリース前は、ブランチもPRも作らない」「自分の判断で新たに Issue や PR を
> 作らないこと」のような記述。開発初期のリポジトリでは珍しくない。

### 3. 起票内容を固める

材料は次の順で拾う。

1. **このセッションでの調査結果** — 直前に読んだコード、再現させたエラー、失敗したテスト。
   これが一番強い材料。`file:line` まで押さえる。
2. **ユーザーの指示** — 曖昧なら、書き始める前に *何が困るのか* を1つだけ聞く。
3. **コードの実地確認** — 影響範囲を書くなら `grep` で実際に呼び出し箇所を数える。

次が埋まっていれば起票できる。埋まらない項目は空欄のまま残す（埋めすぎない）。

- **何が起きているか**（バグなら現象、タスクなら現状）
- **なぜ困るのか**（影響。これが書けないなら起票する価値を再考する）
- **どこか**（`file:line`、画面名、URL）

### 4. 重複を確認（GitHub のみ）

**同じ issue が既に立っていないか必ず調べる。** 重複起票はノイズになる。

```bash
gh issue list -R <owner/repo> --state all --search "<キーワード>" --limit 10
```

キーワードは関数名・ファイル名・エラー文言など具体的なものを2〜3通り試す。
近いものが見つかったら、起票せずそのissue番号をユーザーに提示し、
「新規で立てるか、既存にコメントを足すか」を確認する。

### 5. 既存 issue の書式に倣う

そのリポジトリの直近の issue を読み、見出し構成・粒度・言語（日本語/英語）を合わせる。

```bash
gh issue list -R <owner/repo> --limit 5 --json number,title
gh issue view <番号> -R <owner/repo> --json title,body --jq .body
```

`.github/ISSUE_TEMPLATE` があればそちらが優先。無ければ下の**テンプレート**章を使う。

**タイトル**: 症状か作業内容を、それ単体で読んで分かる具体さで書く。1行で完結させ、
末尾に句点を付けない。チケット番号の接頭辞は、そのリポジトリの既存issueが付けて
いなければ付けない。

- 良い: `parseDate が空文字に Invalid Date を返し、一覧の並び替えが先頭に寄る`
- 悪い: `バグ修正` / `formats.ts の件`

### 6. ラベルを選ぶ（GitHub のみ）

```bash
gh label list -R <owner/repo>
```

- **一覧に出たラベルからのみ選ぶ。無いラベルは付けず、新規作成もしない。**
- 優先度ラベルがあるリポジトリでも、**優先度は自分で決めずユーザーに確認する。**
- 判断がつかなければラベル無しで作る。後から付けられる。

### 7. 提示して確認（ハードストップ）

次を提示して、**ターンを終了し承認を待つ**。

- 起票先リポジトリ（`owner/repo`）
- タイトル
- 本文の全文
- 付けるラベル / assignee（あれば）
- 手順4で見つかった類似issue（あれば）
- **裏が取れず空欄にした項目**（黙って省略しない）

### 8. 作成（承認後の別ターン）

```bash
gh auth status
```

認証済みなら、本文を一時ファイルへ書き出してから作成する（本文の記号がシェルに
壊されないよう、`--body` ではなく `--body-file` を使う）。

```bash
gh issue create -R <owner/repo> \
  --title "<タイトル>" \
  --body-file /tmp/issue_body.md \
  --label "<ラベル>"
```

- 作成後、返ってきた issue の URL をユーザーに返す。
- assignee を指定するなら `--assignee @me`。指示が無ければ付けない。

### 9. フォールバック（GitHub 以外 / `gh` 未認証・未インストール）

**Bitbucket などのリポジトリでは `gh` は使えない。** 起票を諦めるのではなく、生成した
タイトルと本文を Markdown のまま出力し、ユーザーがそのまま貼れる形で渡す。そのうえで、
どこに起票する想定かを一言添えて確認する（そのホストの Issues か、Jira 等の別チケット
システムか）。

GitLab で `glab` が入っていれば `glab issue create` が使える。無ければ同じく Markdown を出力する。

`gh` が未認証の場合も同じくMarkdownを出力し、`gh auth login` が要る旨を伝える。

## テンプレート

該当しないセクションは**丸ごと省く**。空の見出しだけ残さない。

### バグ

````markdown
## 概要

（何が・なぜ壊れているかを1〜3文。原因が分かっていれば `file:line` 付きで）

## 現象

（利用者から見て何が起きるか。エラーが出るならそのまま貼る）

```
Error: ...
  at ... (path/to/file.tsx:80)
```

### 再現手順

1. （具体的なURL・データ・操作で。「〜すると」で濁さない）
2.

## 影響範囲

（`grep` で確認した実際の呼び出し箇所を列挙）

- `path/to/a.ts`
- `path/to/b.ts`

## 原因 (path/to/file.ts:177-182)

```ts
（該当コードを引用）
```

（なぜそれが原因かを1〜2文）

## 暫定対応

（既に回避策を入れているなら、そのPR番号と内容。無ければこの節ごと省く）
````

### タスク / 改善 / 技術的負債

````markdown
## 概要

（何をするか・なぜ必要かを1〜3文）

## 現状

（今どうなっているか。調査済みなら該当ファイルを列挙）

## やること

- [ ] （作業単位で。手が付けられる粒度に割る）
- [ ]

## 補足

（判断が必要な論点、未確認事項。**確認していないことは「要精査」と明記する**）
````

## 初めて触るリポジトリで最初に見ること

**リポジトリ固有の値をこのスキルに書き溜めない。** ホスト・ラベル・テンプレート・
既定ブランチはリポジトリごとに違い、時間でも変わる。毎回コマンドの出力を正とする。

```bash
git remote get-url origin                             # ホストと owner/repo
gh repo view --json defaultBranchRef --jq .defaultBranchRef.name   # 既定ブランチ
ls .github/ISSUE_TEMPLATE 2>/dev/null                 # テンプレートの有無
gh label list -R <owner/repo>                         # 実在するラベル
gh issue list -R <owner/repo> --limit 5               # 運用されているか、書式の傾向
```

判断の目安。

- `gh issue list` が空 → そのリポジトリは Issues を使っていない可能性がある。
  起票先が合っているかユーザーに確認する
- 優先度ラベルがある → 優先度は自分で決めず、手順7でユーザーに確認する
- `.github/ISSUE_TEMPLATE` がある → 下のテンプレートより優先する
- remote が `github.com` 以外 → 手順9のフォールバックへ

リポジトリごとの事情（起票の可否、貼り先、命名の癖）は、このスキルではなく
**そのリポジトリの `CLAUDE.md`** に書く。そちらは手順2で必ず読む。
