# release-pr

`main` に溜まった変更を `release`（本番）へ取り込む PR を、**承認を得てから** 作成する。

## create-pr との違い

同じ「PR を作る」だが、入力も本文の価値も別物なので、混ぜると必要な確認が落ちる。

| | `create-pr` | `release-pr`（これ） |
|---|---|---|
| base ← head | `main` ← 作業ブランチ | `release` ← `main` |
| 差分の性質 | 未レビューの新しいコード | 全部レビュー・CI 済み |
| 本文の価値 | 何をしたか・なぜそうしたか | **マージ後に本番が動く前提が揃っているか** |
| マージの意味 | dev に入る | **本番へデプロイされる** |

作業ブランチを `release` へ向ける PR は作らない。`release` へ向けてよいのは `main` からの
リリース PR だけで、本番へ出す判断はリリース作業であって機能開発の一部ではない。
頼まれても、それは `main` 行きの PR にすべきだと伝える。

## 絶対原則

- **本文を提示して承認を得るまで作成しない。** 提示（手順8）と実行（手順9）は必ず別ターン。
  手順8を出したらターンを終了して返信を待つ。この PR のマージは本番デプロイのトリガーで、
  通常の PR より一段重い。「リリース PR 出して」は通常のトリガーであって確認スキップ指示ではない。
- **「マージ前に必要な作業」を空欄のまま出さない。** 何も要らないなら「なし」と書く。空欄は
  「無い」ではなく「調べていない」と読まれ、読み手が自分で調べ直すことになる。この節が
  リリース PR の存在理由なので、ここが埋まっていない本文は出す意味がない。
- **`release` 側に `main` へ未反映のコミットが無いか必ず確かめる**（手順3）。あるのに気づかず
  進めると、本番だけに当たっていた修正を巻き戻す。
- **やっていない確認を「確認済み」と書かない。** Vercel の設定状況・本番 DB の適用状況は
  リポジトリからは見えない。見えないものは「未確認」か、ユーザーに聞いて答えをもらってから書く。
- **squash しない。** 取り込みは merge commit。squash すると `main` 側のコミットが1つに潰れ、
  以降 `git log origin/release..origin/main` が未反映の実態を映さなくなる。次のリリースで
  「何が未反映か」を数える手段が壊れる。
- **マージはしない。** 本番へ出す判断は人がする。PR を作って URL を返すところまでが持ち場。
- 機微情報（キー・トークン・本番の内部URL）を本文に書かない。環境変数は**名前と要否**を書き、
  値は台帳（ドキュメント）を指す。

## 手順

### 1. リポジトリと運用を確定する

```bash
git remote get-url origin                    # ホスト判定と owner/repo
git fetch origin main release                # 以降の比較は origin/* を正にする
git branch -r | grep -E 'origin/(main|release)$'
```

`release` が無ければ、このスキルの対象ではない。base=`main` の運用として `create-pr` に渡す。

**`owner/repo` を取り出し、以降の `gh` には必ず `-R owner/repo` を渡す。** 別リポジトリの
ディレクトリから呼ばれても取り違えないため。`github.com` 以外（Bitbucket など）では `gh` が
使えないので、本文まで作って手順10のフォールバックで出す。

そのリポジトリの運用も読む。**リポジトリ固有の値をこのスキルに書き溜めない。**

```bash
cat .github/PULL_REQUEST_TEMPLATE/release.md 2>/dev/null   # あれば本文の正本
grep -nE "release|本番|Production|ブランチ運用" CLAUDE.md README.md 2>/dev/null | head -20
```

### 2. 分岐（ここで進路が3つに分かれる）

**手順3以降は「出す差分がある」前提の作業。** 先にこの2コマンドで進路を決める。上から順に
読んで手順9まで来てから引き返すのは、まるごと無駄になる。

```bash
git log --oneline origin/release..origin/main | wc -l                          # 未反映の量
gh pr list -R <owner/repo> --state open --base release \
  --json number,title,headRefName,createdAt --jq '.[]|"#\(.number) \(.title) (\(.createdAt))"'
```

| 結果 | 進路 |
|---|---|
| 未反映 0 件 | **作らない。** 下の「出すものが無いとき」へ。手順3以降は飛ばす |
| open な PR がある | **新規作成ではなく本文の更新。** 下の「既に開いているとき」を読んでから手順3へ |
| どちらでもない | そのまま手順3へ |

#### 出すものが無いとき（未反映 0 件）

本番は既に `main` と同じ。**PR を作らないと決めたときの成果物は、根拠つきの一言と次の一手**で、
本文をひねり出すことではない。次を返す。

- `origin/release` と `origin/main` が同じ位置にあること（コミットハッシュを添える）
- 前回のリリースがいつ・どの PR で入ったか
- `main` 未マージの open PR があるなら、それがリリース候補である旨（`main` に入れるのが先）

**ついでに、前回のリリースの記録が `release` に残っているかを見る。** 0 件ルートでは
手順3を読まないので、ここで1回だけ確かめる。

```bash
gh pr view <前回のリリース PR 番号> -R <owner/repo> --json mergeCommit --jq .mergeCommit.oid
git branch -r --contains <その SHA>          # 何も出なければ、その履歴は捨てられている
```

マージコミットがどのブランチからも辿れないなら、マージ後に `release` が force push か
reset で `main` の先端へ揃えられている。ツリーが同じなら本番の中身は無事だが、
**この運用を続けると `git log origin/release..origin/main` で未反映を数える手段が壊れる**
（数えられているのは、たまたま今回そうなっていないから）。見つけたら伝える。

**「直したのに本番で直っていない」と言われて呼ばれた場合、ここで話が変わる。** 未反映が
0 なら原因は取り込み漏れではないので、デプロイの成否・キャッシュ・環境変数を見る方向へ
切り替える。リリース PR を作ってお茶を濁さない。

#### 既に開いているとき

同じ base ← head の PR は GitHub が2本目を弾くし、仮に作れてもどちらを見ればよいか
分からなくなる。やることは本文の更新で、手順3以降はそのまま使える。

**その PR のチェック状況を、この時点で見る。**

```bash
gh pr checks <番号> -R <owner/repo>
gh pr view <番号> -R <owner/repo> --json headRefOid,createdAt,mergeStateStatus
```

赤いまま止まっているなら、**それがそのリリースの最重要事項**で、本文をどう直すかより先に
伝えるべきこと（多いのは、`main` 側に未マージの修正 PR があってブロックされている形）。
本文だけ直して赤に触れないと、読み手はマージできる状態だと思って待つことになる。

**PR を開いたあとに `main` が進むのも普通に起きる。** `headRefOid` が今の `origin/main` と
一致しているかを見る。ずれていれば、その差は本文に無いまま本番へ出る。

更新の実行も承認を取ってから（手順8・9）。

#### `main` 側に未マージの修正 PR があるとき

赤の原因が `main` 側の未マージ PR だったり、リリース前に入れるべき修正が別に開いていたり
すると、**その PR が `main` に入った時点でリリース PR の head が動く。** 本文をどう書くかで
迷うが、答えは決まっている。

**いまの head の内容で正直に書く。** そして、その修正 PR を「マージ前に必要な作業」の
**先頭**に置き、`main` に入ったら本文とタイトルを作り直す旨を添える。

先取りして「修正済みの状態」で書かない。書いた時点では本番へ出る中身に含まれておらず、
**マージの順番を1つ間違えると、本文と実際に出るものが食い違う。** リリース PR の本文は
「この PR をいまマージしたら何が本番へ出るか」を表していないと意味がない。

最も古い未反映コミットの日付は本文に入れる。**何週間ぶんが一度に出るのかが、リスクの目安**になる。

```bash
git log --format='%ad %s' --date=short origin/release..origin/main | tail -1
```

### 3. `release` 側に固有の変更が無いかを確かめる

```bash
git log --oneline origin/main..origin/release       # release 側にだけあるコミット
git diff --stat origin/main...origin/release        # そのコミットが持ち込んでいる中身
```

**見るのは「コミットがあるか」ではなく「固有の中身があるか」。** merge commit で取り込む運用
では、前回のリリース PR のマージコミットが `release` 側に必ず1つ残る。つまり
`git merge-base --is-ancestor origin/release origin/main` は**毎回 false になり、
fast-forward は基本できない**。これは正常な定常状態で、事故ではない。

`git diff --stat origin/main...origin/release` が**空なら固有の中身は無い。** そのまま手順4へ
進み、本文には「`release` 側に固有の変更なし（前回のリリースのマージコミットのみ）」と書く。

空でなければ、`release` にだけ存在する変更がある。**それが何かを突き止めるまで進めない。**
候補は3つで、どれも扱いが違う。

- **本番だけに当てた hotfix** — `main` に取り込む PR を先に出す。放置すると、この
  リリースのマージで本番から消える。**消えたことに誰も気づけない**のが怖いところ
- **squash マージの残骸** — 内容は `main` にもある。本文に「内容は同一」と根拠つきで書く
- **事故**（誰かが `release` へ直接 push した） — 何が入ったかを本人に確認する

`git log -p origin/main..origin/release` で中身を見て判断する。「マージすれば消えるから」で
飛ばさない。

逆向きの事故もある。`release` の履歴に前回のリリース PR のマージコミットが**無い**場合
（`git log origin/release` が直線で、`gh pr view <前回> --json mergeCommit` の SHA が
どのブランチにも無い）、マージ後に `release` が force push か reset で `main` の先端へ
揃えられている。ツリーが同じなら本番の中身は無事だが、**この運用を続けると
`git log origin/release..origin/main` で未反映を数える手段が壊れる**ので、見つけたら伝える。

### 4. 含まれるものを PR 単位で拾う

```bash
git log --merges --first-parent origin/release..origin/main --pretty='%s'   # merge commit の件名
gh pr list -R <owner/repo> --state merged --base main --limit 30 \
  --json number,title,mergedAt --jq '.[]|"\(.number) \(.title) \(.mergedAt)"'
```

merge commit の件名から `#番号` が拾える。squash 運用のリポジトリでは件名の末尾に `(#12)` が
付く。どちらも取れなければ `gh` の一覧と手順2の日付で突き合わせる。

**コミット単位ではなく PR 単位でまとめる。** 読み手（本番へ出す判断をする人）が知りたいのは
「どの機能が出るか」で、コミットの粒度は `main` のレビューで既に消化されている。
番号を残すのは、レビュー済みであることを辿れるようにするため。

### 5. 前提の棚卸し（ここが本題）

差分は `main` へのマージ時にレビューも CI も通っている。**リリースで壊れるのはコードではなく、
コードが前提にしている外部の状態。** そこだけを機械的に洗う。

**まず、そのリポジトリの前提がどこに書かれているかを探す。** 置き場は5サイトでも揃って
いない（環境変数の台帳が `docs/md/ENVIRONMENT_VARIABLES.md` のリポジトリ、
`00_docs/<name>-env-vars.md` のリポジトリ、台帳を持たないリポジトリがある。`docs/sql/` や
`proxy.ts` に至っては**無いリポジトリのほうが多い**）。決め打ちで grep すると空振りする。

```bash
git ls-files | grep -iE 'env|\.sql$|migration|proxy\.|middleware\.' | head -20
ls .github/workflows/
```

**見つかったパスで、差分を洗う。**

```bash
git diff --stat origin/release...origin/main | tail -1
git diff --name-only origin/release...origin/main | grep -iE '<上で見つかったもの>'
git diff origin/release...origin/main -- '*env*' | grep -E '^[-+].*(process\.env|=)' | head
```

差分は3つドット（`...`）。マージベースからの差分になり、PR 画面に出るものと一致する。

洗う対象は4つ。

**環境変数** — 台帳・`env` を読む層（`lib/env.ts` など）・`.env.example` に差分があったら、
増えた変数を名前で挙げる。Production スコープに入っているかは**リポジトリからは確認できない**。
管理者の管轄で開発側から変更できないなら、依頼済みか未依頼かも書く。未設定だと何が起きるか
（ビルドが落ちる／その機能だけ無効になる）まで書けると、読み手が優先度を判断できる。
変数が増えていなくても、**既存の変数の使われ方が変わることがある**（値が URL の基準に
昇格した、必須になった）ので、`env` を読む層の差分は中身を見る。

**DB マイグレーション** — SQL の追加があれば要注意。Git では配られないので、適用は人手で、
しかも環境ごと。**適用済みかどうかはリポジトリからは分からないので、ユーザーに聞く。**
本番 DB を直接読んで確かめようとしない（塞がれているうえ、聞けば1往復で済む）。

**外部サービス** — 計測ID（設定した環境で計測が始まる）、認証キー、親サイト側の掲載や
リダイレクト設定。`proxy.ts` / `middleware.ts` に相当するものの差分は、公開範囲そのものが
変わる合図。

**この PR に CI が付くか** — ワークフローの `pull_request` の `branches` に本番ブランチが
入っていないと、**この PR には CI が1つも回らない。** 本番へ出す PR にだけ CI が無い状態で、
手順8で必ず伝える必要があるので、作成後ではなくここで見る。

```bash
git show origin/main:.github/workflows/<name>.yml | grep -A6 'pull_request'
```

入っていなければ、直すなら `branches: [main, release]`。Vercel の Preview ビルドだけが
唯一のシグナルになる場合も、そう伝える（そのビルドが偽の赤を出すリポジトリもある）。

洗った結果が空なら「なし」と書く。**空欄では「調べていない」と読まれる。**

### 6. 本番の挙動が変わることを拾う

ユーザーに見える変化だけを別立てにする。内部の整理は手順4側で足りる。

見落としやすいのは、コードの意味は変わっていないのに**環境が変わることで初めて効く**もの。

- 認証ゲート（Basic 認証・プレローンチの目隠し）の撤去 → 公開範囲が変わる
- 課金・上限・無料枠の変更 → 既存ユーザーの見え方が変わる
- 計測の開始（ゲートが外れて初めて計測が走る、など）
- 外部への送客URL・OGP → 他サイトから見えるものが変わる

無ければ「なし」。**あるのに書かないと、後で本番の問い合わせとして返ってくる。**

### 7. マージ後の確認と切り戻しを書く

**マージ後の確認**は、本番で実際に踏む操作を番号付きで書く。デプロイの完了確認だけで済む
リリースならそう書く。手順5・6で挙げたものには、それぞれ対応する確認があるはず（環境変数を
足したなら、その機能を1回通す。DB に触ったなら、行が増えることを見る）。

**切り戻し**は、出したあとで戻す手段を書く。

- Vercel はデプロイ単位で戻せる（Instant Rollback）。コードだけのリリースならこれが最速
- `release` を revert する PR を出す手もあるが、次のリリースで再度取り込む形になる
- **マイグレーションを含むリリースは戻せない。** 適用済みのスキーマは戻らないので、
  「コードは戻せるがデータは戻らない」と明記する

### 8. 本文を組んで提示する（ハードストップ）

`.github/PULL_REQUEST_TEMPLATE/release.md` があれば**見出しをそのまま使い、順序も変えない**。
無ければ下のテンプレート章を使う。HTML コメントの中身は必ず読む（運用ルールが書かれている）。

**タイトルは `release: <内容の要約>`。** 日付は入れない（GitHub が作成日を持っている）。
1行で完結させ、末尾に句点を付けない。何が出るのかが一覧で分かる具体さにする。

- 良い: `release: 履歴の文言修正・プラン比較表の修正ほか`
- 悪い: `release: main を release へ` / `本番リリース` / `chore: 取り込み`

次を提示して、**ターンを終了し承認を待つ**。

- 作成先（`owner/repo`）と **base `release` ← head `main`**
- タイトルと本文の全文
- **手順5で挙げた、マージ前に人がやる必要のあること**（ここが提示の主目的）
- 手順3で FF 不可だったなら、その正体と扱い
- CI が回るかどうか（手順9で見る）
- **裏が取れず「未確認」にした項目**（黙って省略しない）

### 9. 作成する（承認後の別ターン）

push もブランチ作成も不要。`main` は既に `origin` にある。

```bash
gh pr create -R <owner/repo> --base release --head main \
  --title "release: ..." --body-file <本文のパス>
```

**本文は一時ファイルに書き出してから渡す**（記号がシェルに壊されないよう `--body` は使わない）。
置き場は作業環境の一時ディレクトリ（scratchpad が指定されていればその中、無ければ `/tmp`）。
**リポジトリの中には置かない。** 作業ツリーを汚す。

手順2で既存の open な PR を見つけていたなら、`gh pr create` ではなく
`gh pr edit <番号> -R <owner/repo> --title "release: ..." --body-file <本文のパス>` で
本文を差し替える。

**CI の結果を見る**（回るかどうかは手順5で確かめてある）。

```bash
gh pr checks <番号> -R <owner/repo>
```

落ちていたら伝える。緑になるまで放置しない。**手順5で「CI は付かない」と分かっている
リポジトリでは、チェックが空であること自体が想定どおり**なので、そう添える。

### 10. 引き継ぐ

- **マージは人がやる。** merge commit で取り込む（squash しない）ことを添える
- マージ後、手順7に書いた確認を誰が踏むのかをはっきりさせる
- `gh` が使えないリポジトリでは、タイトルと本文を Markdown のまま出力し、base と head を添える

## テンプレート（リポジトリに無いとき）

リポジトリの `.github/PULL_REQUEST_TEMPLATE/release.md` があればそちらが正本。
無いときはこの形で組む。**該当しない節は丸ごと省かず、「なし」と書く。** リリース PR では
「無いことを確認した」自体が情報になる。


## 初めて触るリポジトリで最初に見ること

```bash
git branch -r | grep -E 'origin/(main|release)$'         # release があるか
git log --oneline origin/release..origin/main | wc -l    # 未反映の量
gh pr list -R <owner/repo> --state open --base release   # 既に開いていないか
git merge-base --is-ancestor origin/release origin/main  # FF 可否
ls .github/PULL_REQUEST_TEMPLATE/ 2>/dev/null            # テンプレートの有無
gh pr list -R <owner/repo> --state merged --base release --limit 5 --json title,body
```

最後の1つが効く。**前回のリリース PR が、そのリポジトリで何を確認すべきかの一覧になっている。**
環境変数の表、マージ後の手順、そのとき未確認だったこと——次に見る先はだいたいそこに書いてある。

判断の目安。

- `release` が無い → 対象外。`create-pr` に渡す
- 未反映が 0 → 作らない。本番は `main` と同じ
- open のリリース PR がある → 新規作成ではなく、その本文を `main` の現状に合わせて更新する
- FF 不可 → 手順3。正体が分かるまで進めない
- 前回のリリース PR に環境変数の表がある → 今回も同じ台帳を見る
