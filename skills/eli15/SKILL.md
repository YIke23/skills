# eli15

読み手は、頭は悪くないがこの分野を知らない15歳。専門書ではなく新書を書く。

## 専門書と新書の違いは、情報量ではなく取捨選択

専門書は、読者が自分で必要な箇所を選べるように全部載せる。だから網羅と正確さが正義になる。
新書は逆で、著者がすでに選び終えた結果だけを出す。何を書かないかを決めるのが仕事の本体。

モデルが放っておくと専門書になるのは、抜けがあることを失点だと感じるからだ。
このスキルでは、抜けは失点ではない。全部書いてあって読み通せない方が失点になる。

書き切れなかったものは最後の「もっと知りたい人へ」に置き場所がある。
そこに逃がせば本文から外して構わない。

## 平易にすることは、薄めることではない

ここを取り違えると、内容を削って初心者向けを装っただけのものが出る。

GOV.UK の言い方が正確だ。**開いて見せるのであって、程度を下げるのではない**。
実質・機微・精度は全部残す。剥がすのは、読みにくくしている側だけ
——専門用語、長い文、抽象名詞、入り組んだ構造。

「相手が詳しくないから内容を落とす」も「相手が専門家だから密に書く」も、どちらも間違い。
GOV.UK の調査では、平易な英文を好むと答えた人が8割で、**論点が複雑なほどその傾向が強く、
学歴が高く専門性が高い人ほど平易さを好んだ**。専門家は複雑な文章を読めるが、
代わりがあるなら読みたくない。読む量が一番多いのが彼らだからだ。

専門用語そのものは禁止ではない。必要なら使う。それは jargon ではない。
初出で1行の言い換えを添える、それだけが条件。

## 出力の型

単一のHTMLファイル1枚。次の4部構成にする。

**1. つかみ(1〜2文)**
そのトピックで一番意外な事実か、素朴な疑問から入る。定義から始めない。
「Xとは〜である」で始まった時点で新書ではなく教科書になっている。

**2. 山を3つまで(各1節)**
節はどれだけ多くても3つ。ここが取捨選択の主戦場になる。
4つ目を書きたくなったら、それは3つのどれかに畳めるか、本文から外すべきものかのどちらか。
各節は「1節=1つの言いたいこと」。節タイトルは体言止めではなく、言いたいことを文で書く。
例: ×「キャッシュの仕組み」 ○「同じ計算を2度させないための引き出し」

**3. で、結局(1〜3文)**
読者が明日誰かに話せる形で1文にまとめる。本文の要約ではなく、持ち帰る一言。

**4. もっと知りたい人へ(3項目)**
本文から外した論点を、行き先つきで置く。ここがあるから本文を削れる。
各項目は「何が待っているか」を1行で。リンクやファイルパスがあれば添える。

## 分量の予算

| 項目 | 予算 |
|---|---|
| 本文合計 | 1,600字まで(目安1,300字) |
| 節 | 3つまで |
| 1節 | 350〜500字 |
| 1文 | 60字以内(目標40字) |
| 1段落 | 3文以内 |
| 図 | 2〜4点 |

一文の長さは効き目が大きい。GOV.UK は15〜20語を標準、25語を上限としている。
平均14語なら読者は9割以上を理解し、43語では1割を切る、という調査が根拠だ。
日本語ではおよそ40字が標準、60字が上限にあたる。修飾を積むより、文を切る。

守るべきは上限のほうで、下限はない。題材が単純なら短くてよい。
分量を満たすために節を足したり、言い換えを重ねたりしない。
問いが2文で片づくなら2文で終える。それも取捨選択の結果だ。

出力言語は、依頼された言語に合わせる。

## 文章の作法

- 能動態で書く。誰が何をするかを言う。受動態は文を長くする
- 短い語を選ぶ。「実施する」より「やる」、「about」の意味で「approximately」を使わない
- 左揃え。両端揃えは使わない。ブラウザの組版では語間が崩れる
- 太字や斜体を長く続けない。可読性が落ちる。強調したい塊はカードとして外に出す
- 大文字の連続は数語まで。見出しや本文を大文字にしない

## 図

図は飾りではなく、文章で書くと長くなるものを引き受けさせる担当。
逆に言えば、図を1点入れたら本文がその分短くなっていないとおかしい。

内容の形に合わせて選ぶ。

| 伝えたいこと | 向いている図 |
|---|---|
| 順序・流れ | 横並びのステップ(矢印つき) |
| 構造・包含関係 | 入れ子のボックス |
| 比較・対比 | 2カラムの並置 |
| 量やコストの差 | 長さで見せるバー |
| 分岐・条件 | 簡単な樹形図 |
| 前後の変化 | before/afterの並置 |

実装はインラインSVGで行う。外部CDNやライブラリを読まないので、
ファイル1枚をそのまま渡せて、オフラインでも開ける。

色は `assets/base.css` の `.box` `.t` `.t-sub` などのクラスから引く。
`fill="#..."` の直書きはテーマを切り替えても変わらず、ダークで図だけ取り残される。

図には必ず短いキャプションを付ける。図だけ見た人が何の図か分かるように。

## デザイン

**Neobrutalism で固定**。毎回作り直さない。`assets/base.css` の中身を `<style>` に
そのまま貼り、必要な分だけ足す。色は全組み合わせをライト/ダーク両方で測ってあるので、
値を勝手に変えない。変えたくなったら
`python3 ${CLAUDE_SKILL_DIR}/scripts/check_contrast.py ${CLAUDE_SKILL_DIR}/assets/base.css`
で測り直してから変える。

このスタイルの決まりごとは3つだけ。

- **枠と影**: 3px の実線と、ぼかさない5pxのオフセット影。同じ濃紺一色で引く
- **余白は詰めない**: 枠と影が濃いので、カードの内側は 24〜32px 取る。詰めると窮屈になる
- **琥珀ブロックの上は暗い文字のみ**: 明るい文字は 4.5:1 を絶対に通らない。`.t-a` を使う

フォーカスの見え方だけ注意が要る。装飾の枠線が濃いので、同じ見た目にすると埋もれる。
`base.css` では差し色のアウトラインを外側に出してある。消さない。

見出しの階層はサイズだけで作らない。太さと色も一緒に動かす。

## 品質ライン

- 本文16px以上、行間1.7以上、1行は38em程度(日本語で約38字、英字で約76字)
- コントラスト比は本文も図中の文字も 4.5:1 以上。ライトとダーク両方で満たす
- `color-scheme` を宣言する。無いとブラウザが勝手に反転させ、誰も設計していない配色になる
- スマホ幅で横スクロールが出ない
- `prefers-reduced-motion` を尊重する
- 見出しは `h1`〜`h3` を階層通りに使う

コントラストは目で見て判断しない。淡い色を色付きの箱に載せた瞬間に基準を割ることがあり、
これは見た目ではまず気づけない。同梱の `check_contrast.py` が、CSSの組と、
SVG内の文字を実際に囲んでいる図形との組を座標から割り出して比を出す。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/check_contrast.py article.html
```

`<text>` の座標が実際にどの図形の内側にあるかを見て、その図形の `fill` を下地として測る。
ライトとダークの両方を回すので、片方だけ落ちる事故も出る。終了コードは
0=問題なし / 1=警告 / 2=不適合。**2 が出たまま納品しない。**

配色を変えたくなったときは、記事ではなく `assets/base.css` を直接渡せば配色だけ測れる。

## コードベースを説明する場合

一般トピックとの違いは、読む工程が先に入ることだけ。書き方の型は同じ。

1. 該当のディレクトリとエントリポイントを実際に読む
2. 「このコードが存在する理由」を1文で言えるまで読む。言えないうちは書かない
3. 3つの山を選ぶ。ファイル構成をなぞらない。読み手が引っかかる順に選ぶ
4. ファイルパスは本文に散らさず、「もっと知りたい人へ」にまとめる

推測で埋めない。読んで分からなかったことは、分からなかったと書く方が新書として誠実で、
読み手が次にどこを見ればいいかも分かる。

## 専門書に戻りかけているサイン

書いたあとに自分の出力を読み返して、次が出ていたら削るか畳む。
どれもモデルが「正確であろうとした」結果として出るもので、悪意なく混入する。

- 「ただし」「なお」「〜の場合は」で始まる例外の説明が3つ以上ある
- 定義せずに使った専門用語がある
- API名・オプション名・バージョン番号が並んでいる
- 「一般に」「基本的には」「多くの場合」で始まる保険がかかった文がある
- 箇条書きが6項目を超えている
- 60字を超える文がある
- 節が4つ以上ある

例外や網羅性は、本文ではなく「もっと知りたい人へ」の担当。
