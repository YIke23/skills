# 取捨選択 — 何を落とし、何を残すか

SKILL.md §3 の判断に迷ったとき読む。基準は一つしかない。

> この段落は、読者の判断や作業を変えるか。
> 変えないなら、それは書いた本人にしか価値がない情報である。

以下は、このテストにかけても手が止まりやすい典型例と、その捌き方。

---

## 経緯を残したくなったとき

一番よく起きる。調べるのに3時間かかった道筋を、1行に圧縮するのは惜しい。
だが読者にとって、採らなかった道の詳細は**読む必要のない3時間**でしかない。

**判断:** 経緯は、それが読者の判断を変えるときだけ残す。変えるのは次の場合だけ。

- 読者が同じ選択肢を再検討しそうなとき（「なぜ X を使わないのか」と必ず聞かれる）
- 失敗が再現しうるとき（同じ罠を踏む）
- 前提が変われば結論も変わるとき（「Y が解決されたら再検討の余地あり」）

このいずれでもない経緯は、結論と一行の理由に畳む。

**例:**

- 悪い: 「まず A を試したが、B の制約で断念した。次に C を検討し、ドキュメントを読んだところ D という記述があり……（8段落）……最終的に E を採用した」
- よい: 「E を採用した。A は B の制約で使えず、C は D のため見送った。詳細は [検討経緯](./auth-appendix.md)」

畳んだ経緯は捨てずに付録へ逃がす。消したのか、そもそも検討していないのかが
読者に区別できないと、同じ調査をやり直させることになる。

## 表にまとめたくなったとき

表は情報を整理した気分になれるが、**軸が2本ないものを表にすると水増しになる。**
「項目 / 説明」の2列表は、たいてい箇条書きですらなく、地の文で書くべき内容。

**判断:** 比較軸が2本以上あり、読者がセル単位で行き来するなら表。
上から順に読むだけなら地の文。

なお表の中身は字数に数えない（`count.py` が除外する）。これは表を無制限に
使ってよいという意味ではなく、**必要な比較表を字数のせいで削らせないため**の措置。
水増しの表は字数に出ないぶん、自分で気づくしかない。

---

## 網羅したくなったとき

「全部書いておけば漏れがない」は、読者ではなく書き手の安心のための動機。
網羅は読者の探索コストを上げるので、たいてい逆効果になる。

**判断:** 列挙は、読者が**その全部を見る必要があるとき**だけ全部書く。
そうでなければ、代表例を3つと「他は〈場所〉を参照」に畳む。

- 全部要る例: 手順のステップ、必要な権限、チェックリスト
- 畳んでよい例: 使えるオプションの一覧、影響を受けたファイルの全列挙、関連リンク集

---

## コードをどれだけ貼るか

コードブロックは字数に数えないので、いくらでも貼れてしまう。だが読者の
読解コストは字数と無関係に増える。

**判断:** 貼るのは、読者が**そのまま実行・コピーするもの**と、
**説明対象の中心**だけ。前後の文脈は行数で示してリンクする。

- よい: 実行するコマンド、設定ファイルの該当ブロック、エラーメッセージの実物
- 避ける: 変更後のファイル全文、diff の全体、動作を説明するためだけの長い擬似コード

30行を超えるブロックが出てきたら、そこは付録に属していないか疑う。

## 前提をどこまで説明するか

§0 で「読者が既に何を知っているか」を書き出してあるはずなので、そこに戻る。
書き出せていないなら、この判断はできない。

**判断:** 読者が既に知っていることは書かない。ツールやサービスの一般的な説明
（「Docker とはコンテナ技術で……」）は、ほぼ常に落としてよい。必要なら公式ドキュメントへ
リンクする。**この文書でしか読めないこと**に字数を使う。

逆に、**この案件固有の前提**は省略しない。「本番の DB は東京リージョンにしかない」
「この API は社内VPN からしか叩けない」のような、調べても出てこない情報こそ
残す価値がある。

## 残す側のチェック

削りきったあと、次が本文に残っているか確認する。抜けていたら削りすぎ。

- [ ] 読者が再現・検証するのに要る固有名詞・パス・コマンド・数値
- [ ] 判断の分岐点と、その採否の理由（各1行以上）
- [ ] 既知の落とし穴（「詰まりやすい所」）
- [ ] 次の一手、または「これで完了」という明示
- [ ] 調べていない範囲・確認していない前提の開示

最後の項目が抜けると、読者は書かれていないことを「確認済み」と読む。
これは削りすぎの中でもっとも高くつく。
