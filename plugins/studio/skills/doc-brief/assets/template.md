## 骨格 — 文書タイプ別

節の名前はそのまま使わず、結論を含む見出しに書き換える。ここにあるのは並び順であって、
ラベルではない。

**並び順も固定ではない。** §0 で決めた「読んだ後に何が起きてほしいか」と衝突したら、
物差しのほうが優先する。例えば引き継ぎで期限つきの作業があるなら、
下の骨格で最後に近い位置にあっても冒頭に出す。型は出発点であって、判断の代わりではない。

### 調査レポート・技術選定

```markdown
## 結論
## そう判断した理由
## 見送った選択肢    ← 案ごとに1〜2行。詳細は付録へ
## 前提と限界        ← 調べていない範囲を正直に書く
## 次の一手
```

読者は結論とその妥当性を確かめに来る。調査の順序どおりに書かない。

### 手順書・ガイド

```markdown
## これは何のための手順か
## 前提（環境・権限・事前準備）
## 手順
## 詰まりやすい所
```

読者は手を動かしながら読む。前提を後半に置くと、失敗してから戻ることになる。
「詰まりやすい所」は書いた本人にしか書けない節で、この文書の価値の大半がここにある。

### 設計・意思決定メモ

```markdown
## 決めたこと
## 背景と制約        ← なぜ今これを決める必要があるか
## 採用案の中身
## 採らなかった案と理由
## 決めていないこと    ← 先送りにした論点を明示する
```

「決めていないこと」を書かないと、読者が「検討済みで問題なし」と誤読する。

### 障害報告・ポストモーテム

```markdown
## 何が起きたか          ← タイトルで原因まで言い切り、ここは1段落
## 影響（誰が・いつからいつまで・何件）
## なぜ壊れたか
## 当日の対応
## 再発防止（済 / 未）    ← 状態を必ず付ける
## 決めていないこと       ← 検討したが結論が出ていない論点
## まだ確認していないこと   ← 調べていない・裏を取れていない事実
```

最後の2つは似ているが別物。**「決めていない」は判断の保留、「確認していない」は
事実の欠落。** 混ぜると、読者が「調べた上で保留した」のか「そもそも見ていない」のかを
区別できなくなる。障害報告ではこの区別が特に効く。

生の時系列ログは本文に展開しない。読者が知りたいのは原因と再発防止で、
分単位の経過は付録に属する。再発防止に状態（済／未／担当未定）を付けないと、
この文書を追跡に使えない。

### 引き継ぎ資料

```markdown
## 担当する範囲
## いま動いているもの（どこに何があるか）
## 継続中の作業と現在地
## 注意が必要な箇所
## 連絡先・権限の在りか
```

未来の読者は文脈をまったく持たない。固有名詞・パス・URL を省略しない。
ここだけは省略が直接コストになる。

## 議事録・スライド構成が必要なとき

この2つは natural-japanese が専用の型を持っている
（`references/doctypes/minutes.md`、`references/doctypes/slide.md`）。
そちらを読んで骨格を借り、ヘッダと字数予算だけこのスキルの規則を当てる。
同じ型をここに写さないのは、片方だけ古くなるのを避けるため。
