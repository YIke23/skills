# readme-builder

README は**リポジトリの入口**で、1枚の読み物ではない。読者はここで「これは何か」「どこに何があるか」
「どう動かすか」「どのブランチに出せばどこに出るか」を知り、続きは README が並べる docs の資料へ行く。
**README は最小限にする。** 章は §3 の7つだけで、それ以外の内容は docs の資料に任せる。

README の事故は、見た目の汚さではなく**嘘と欠落**で起きる。書いた手順は書き手の手元では通る。
.env は書き手の手元にはある。ブランチの運用は書き手の頭の中にある。どれも書き手には見えず、
次の人が最初の10分で踏む。このスキルは材料をリポジトリから拾い、書いた主張を機械と
まっさらな読者で確かめることで、それを止める。

## 0. 誰のために、何を載せるか

読者は2種類いて、欲しいものが違う。

| 読者 | 来た理由 | README を読み終えたときの状態 |
|---|---|---|
| 他のエンジニア | レビュー、連携、障害調査、ついでに見に来た | 5分で「何のリポジトリか・どこに何があるか・次に何を読むか」が分かる |
| 引き継ぐ人 | 明日からこのリポジトリの持ち主になる | 初日にローカルで動く。どのブランチに出せばどこに出るか分かる。続きの資料に辿り着ける |

**README に置くのは §3 の7章だけ。** 環境変数の一覧、デプロイの手順、外部サービスとアカウント、
やってはいけない操作、トラブルシューティング、検証端末への配布手順などは README に書かず、
`docs/`（または `documents/`）の資料に任せて「関連文書」で列挙する。どれも項目が増え続けるか
読む人が限られる内容で、README に置くと膨らみ、docs の資料と二重になって片方が古びる。
**このスキルは docs の資料を作らない。** 書くべき内容がどの資料にも無ければ「まだ確認していないこと」に載せる。

README にも docs にも置かないもの: 環境変数と秘密情報の**値**（ローカル専用の既定値も含む）。
README に置かないもの: 検討の経緯（→ docs かコミット）、引き継ぎ時点の ToDo（→ issue。
README は定常状態を書く）、全ファイルのツリーや依存パッケージの一覧（コードを読めば分かり、
書いた瞬間から古び始める）。

AI エージェント向けの規則は **AGENTS.md** に置き、README の関連文書の下から指す。AGENTS.md は
ツールを問わない共通の置き場所で、CLAUDE.md は `@AGENTS.md` で読み込む側に回す。リポジトリに
CLAUDE.md しか無いときは、AGENTS.md へ寄せるかをユーザーに提案する。CLAUDE.md を無断で動かさない。

## 1. モードを決める

| モード | いつ | やること |
|---|---|---|
| 新規 | README が無い、または中身がほぼ無い | §2 → §5 を通す |
| 書き直し | 構成から作り直す必要がある | 既存から残すべき事実を先に抜き出してから §2 → §5。README から外す内容は、docs に移す先をユーザーに提案する |
| 更新 | コードやブランチ運用の変更に README を追随させる | 変わった箇所と、それに触れる全箇所だけ直す |
| 点検 | 「READMEをレビューして」 | §2 の材料と §5 の検証だけ回し、**書き換えずに**指摘を返す |

依頼から判断できなければ聞く。点検を頼まれて勝手に書き直さない。

## 2. 材料を集める

**書く前に、リポジトリから事実を拾う。** 記憶や「この構成なら普通こうだ」で書くと、
存在しないスクリプト名やブランチ名が紛れ込む。

この SKILL.md を読み込んだディレクトリの `scripts/` を使う（`${CLAUDE_SKILL_DIR}` は空の
ことがあるので使わない。見失ったら `find ~/.claude -path '*/readme-builder/scripts/scan_repo.py'`）。

```bash
python3 <このSKILL.mdのあるディレクトリ>/scripts/scan_repo.py <リポジトリ>
```

出てくるものと、どの章の材料になるか。

| scan の出力 | 使う章 |
|---|---|
| トップレベルのディレクトリ、依存・設定ファイルから推した言語とフレームワーク、モバイルの構成 | ディレクトリ構成 |
| 版指定ファイル、lockfile、compose のサービス、環境変数の雛形 | セットアップ |
| git の remote、既定ブランチ、リモートブランチ（更新の新しい順）、CI、デプロイ設定 | ブランチとデプロイ先 |
| package.json の scripts、Makefile のターゲット、fastlane の lane、EAS のプロファイル | よく使うコマンド |
| docs/・documents/ の資料と、それぞれの見出し | 関連文書 |

**.env 本体は開かない。** 自分でも開かないこと。値を読む必要は無い。
続けて、既存の README・AGENTS.md / CLAUDE.md・docs の資料・CI とデプロイの設定ファイルを読む。
既存 README にしか書かれていない事実は捨てず、README に残すか docs に移すかを決める。

**リポジトリに無い情報は、ユーザーに一度にまとめて聞く。** README に要るのは次の4つ。

- リポジトリの状態（開発中 / 稼働中で保守のみ / 廃止予定）
- 各環境の URL と、それぞれに反映されるブランチ
- ブランチの運用（作業ブランチの切り方、PR が必須か、誰がマージするか）
- セットアップの前提で、リポジトリの外にあるもの（社内の権限申請、VPN など）

聞けない実行（自動化・相手が離席）では止まらない。「まだ確認していないこと」に並べる。
黙って推測で埋めるのが最悪で、未確認と書いてあれば次の人が埋められる。

## 3. 骨格を組む

`assets/template.md` を出発点にする。README の章はこの7つだけで、順番も固定。

1. **冒頭**（見出しなし） — 名前、1〜3文の概要、状態・本番 URL、最終確認日
2. **ディレクトリ構成** — トップレベルのディレクトリだけを1行1役割で、言語・フレームワークも添える。
   15行以内。ファイル単位まで下りない（下りた瞬間から古び始める）
3. **セットアップ** — 前提と、clone から「動いた」までを1回だけ通す手順、成功の目安
4. **ブランチとデプロイ先** — ブランチ / 役割 / マージ先 / デプロイ先（環境と URL）の表と、
   PR の出し方を1行。デプロイの手順そのものは docs の資料に任せる
5. **よく使うコマンド** — セットアップ後に毎日叩くもの（起動・テスト・lint・型チェック・ビルド）を
   コマンド / 用途 の表で。10行以内。scripts や Makefile を全部写さない
6. **関連文書** — docs/・documents/ の資料を**全部**並べる表（資料 / 内容 / いつ読むか）。
   役目を終えた資料（archive/ など）は載せない。表の下に AGENTS.md への案内を1行
7. **まだ確認していないこと** — 聞けなかった項目。全部埋まったら章ごと消す

当てはまらない章は消してよい（ライブラリに「デプロイ先」は無い）。種類ごとの差分は
`references/project-types.md`。更新モードでは既存の見出しを保つ。

**見出しは慣習名でよい。** README は通読されるより、見出しで引かれる。結論を見出しに書くのは
単発の文書の作法で、README では探しにくくなる。

## 4. 書く

- **コマンドはコピーしてそのまま通る形で。** 1ブロック1目的。何が起きれば成功かを1行添える
  （「http://localhost:3000 が開けば成功」）。前提の版は `.nvmrc` や `engines` から写す
- **値は書かない。** 手順は「`.env.example` をコピーする」までにし、入手先は関連文書の資料に任せる
- **ブランチ名・ディレクトリ名・コマンド名は実在するものだけ。** scan の出力から写す。
  「release ブランチがあるはず」のような推測で書かない
- **関連文書の「内容」は資料の見出しと冒頭から1行で、「いつ読むか」は読者が引く場面で書く**
  （「本番に出すとき」「.env を埋めるとき」）
- **検証できない主張は書かない。** 「高速」「本番運用可」は、根拠がリポジトリに無ければ削る
- **言語はチームの文書に合わせる。** 既存 README が中身のある文書ならその言語、数行しかないなら
  AGENTS.md / CLAUDE.md や docs の言語。どれも無ければ日本語。変えたときは報告で言う
- **地の文は 2,000 字が目安。** 超えたら、その内容は docs に属している

## 5. 確かめる

3段で確かめる。どれかを飛ばしたら、報告でそう言う。

### 5-1. 機械で検査する

```bash
python3 <このSKILL.mdのあるディレクトリ>/scripts/check_readme.py <README.md> [--repo <リポジトリ>]
```

下書きをリポジトリの外に置いたときは `--repo` を渡す。相対リンクはリポジトリ直下に置く前提で解決される。

**exit 2（不適合）で止まるもの** — 秘密情報らしき文字列、環境変数の値、手元の絶対パス、埋め残し、
壊れたリンクとアンカー、存在しない npm スクリプト・make ターゲット・fastlane の lane・EAS の
プロファイル（コードブロックと表の中）、元ファイルの無い cp、存在しない compose サービス、
実際の origin と違う clone URL、リモートに無いブランチ名、存在しないトップレベルのディレクトリ。
exit 2 のまま納品しない。

**警告（exit 1）** — 概要・コードブロック・最終確認日・ブランチとデプロイ先の欠落、古い最終確認日、
関連文書に載っていない docs の資料、README に残った docs 向けの本文（環境変数の表、
トラブルシューティングなど）、15行を超えるツリー、2,000 字の超過、モバイルアプリなのに
検証端末の手掛かりが無い、git に入った署名ファイル。1件ずつ読み、意図どおりなら残してよい。

### 5-2. 手順を実際に通す

セットアップから起動・テストまで、**手元で完結するコマンドは実際に叩く**。依存の導入、
lint、テスト、ビルド、ローカル起動がこれに当たる。書いた手順と実際の手順の差はここでしか出ない。

作業ツリーを汚したくないときは、リポジトリを作業用ディレクトリへ複製して（.env 本体は除く）
そちらで通す。Docker を起こせない環境でも、SQLite やホストの処理系で起動とテストまで通せば、
雛形のままでは動かない設定値のような、読んだだけでは見えない欠落が出る。

外部に作用するコマンド（共有 DB へのマイグレーション・seed、デプロイ、課金 API の呼び出し）は
叩かない。叩いていない手順は、報告に「未実行」と書く。「最終確認日」は手順を通した日で、
README を書いた日ではない。手順を通していなければ日付は入れない。

### 5-3. まっさらな読者に読ませる

書き手は文脈を知りすぎていて、欠落が読めない。README **だけ**を渡したサブエージェントに、
引き継ぐ人が最初に抱く質問を答えさせる。手順と質問は `references/cold-reader.md`。
「README からは分からない」と返った質問が欠落で、§2 に戻って埋める。

## 6. 仕上げと報告

- AGENTS.md / CLAUDE.md に README と同じ手順が書かれていたら、正をどちらにするかユーザーに提案する
  （AGENTS.md / CLAUDE.md を無断で書き換えない）
- 既存のファイル名が `readme.md` など小文字なら、改名は `git mv readme.md README.md` で行う。
  macOS は大文字小文字を区別しないので、上書き保存では git 上の名前が変わらない
- 対外公開する README に限り、`natural-japanese:natural-japanese` を `quick <file>` で呼ぶ。
  社内 README には回さない
- 報告は3点だけ: 確かめたこと（5-1〜5-3 の結果）/ 確かめていないこと（未実行の手順、
  未回答の質問）/ ユーザーに決めてほしいこと（README から外した内容の移し先など）

点検モードの指摘は、重い順に「嘘（書いてあるが事実と違う）→ 欠落（無いと作業が止まる）→
置き場所の誤り（docs に属する内容が README にある）→ 古び → 体裁」で並べ、各指摘に行番号と
根拠のファイルを添える。

## 参照ファイル

- `assets/template.md` — README の骨格。章ごとに何を書くかの注記つき
- `references/project-types.md` — Web アプリ・API・ライブラリ・CLI・モノレポ・設定置き場・モバイル・OSS の差分
- `references/cold-reader.md` — まっさらな読者テストの手順と質問
- `scripts/scan_repo.py` — リポジトリから README の材料を拾う。.env 本体は読まない
- `scripts/check_readme.py` — README の主張をリポジトリと照合する。不適合で exit 2
