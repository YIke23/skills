# readme-builder

README は**リポジトリの入口**で、1枚の読み物ではない。読者はここで「これは何か」「どう動かすか」
「困ったらどこを見るか」を知り、続きは README が指す先（docs/・CLAUDE.md・管理画面）へ行く。

README の事故は、見た目の汚さではなく**嘘と欠落**で起きる。書いた手順は書き手の手元では通る。
.env は書き手の手元にはある。担当者は書き手自身だから問い合わせ先を書く発想が無い。
どれも書き手には見えず、次の人が最初の10分で踏む。このスキルは材料をリポジトリから拾い、
書いた主張を機械とまっさらな読者で確かめることで、それを止める。

## 0. 誰のために、何を載せるか

読者は2種類いて、欲しいものが違う。

| 読者 | 来た理由 | README を読み終えたときの状態 |
|---|---|---|
| 他のエンジニア | レビュー、連携、障害調査、ついでに見に来た | 5分で「何のリポジトリか・自分に関係あるか・どこを見ればいいか」が分かる |
| 引き継ぐ人 | 明日からこのリポジトリの持ち主になる | 初日にローカルで動く。本番を壊さずに変更を出せる。困ったとき誰に聞くか分かる |

AI エージェントも README を読むが、**エージェント向けの規則は CLAUDE.md / AGENTS.md に置く。**
README に書くのは、人にもエージェントにも正しい事実だけ。同じ手順を両方に書くと片方が必ず古びるので、
片方を正にしてもう片方からリンクする。

載せるかどうかは、この順で決める。

1. **コードを読んでも分からないこと** — 最優先。なぜ存在するか、外部サービスと秘密情報の置き場所、
   持ち主、デプロイの流れ、やってはいけない操作、知らずに踏む落とし穴
2. **コードを読めば分かるが、入口として要ること** — セットアップと起動のコマンド、前提ツールの版、
   主要な入口ファイル数か所
3. **コードを読めば分かること** — 載せない。全ファイルのツリー、依存パッケージと版の一覧、
   関数の説明。書いた瞬間から古び始め、読者はどれが古いか区別できない

README に置かないもの: 検討の経緯（→ docs/ かコミット）、引き継ぎ時点の ToDo（→ issue か
引き継ぎメモ。README は定常状態を書く）、秘密情報の値（→ 置き場所だけ書く）。

## 1. モードを決める

| モード | いつ | やること |
|---|---|---|
| 新規 | README が無い、または中身がほぼ無い | §2 → §5 を通す |
| 書き直し | 構成から作り直す必要がある | 既存から残すべき事実を先に抜き出してから §2 → §5 |
| 更新 | コードの変更に README を追随させる | 変わった箇所と、それに触れる全箇所だけ直す。構成は変えない |
| 点検 | 「READMEをレビューして」 | §2 の材料と §5 の検証だけ回し、**書き換えずに**指摘を返す |

依頼から判断できなければ聞く。点検を頼まれて勝手に書き直さない。

## 2. 材料を集める

**書く前に、リポジトリから事実を拾う。** 記憶や「この構成なら普通こうだ」で書くと、
存在しないスクリプト名や使っていない環境変数が紛れ込む。

この SKILL.md を読み込んだディレクトリの `scripts/` を使う（`${CLAUDE_SKILL_DIR}` は空の
ことがあるので使わない。見失ったら `find ~/.claude -path '*/readme-builder/scripts/scan_repo.py'`）。

```bash
python3 <このSKILL.mdのあるディレクトリ>/scripts/scan_repo.py <リポジトリ>
```

既存の文書・実行系（scripts / Makefile / compose のサービス / 版指定）・コードが読む環境変数と
雛形の差分・外部サービスの手掛かり・CI・git の remote とコミット数上位が出る。
**.env 本体は開かない。** 自分でも開かないこと。値を読む必要は無い。

続けて、出てきた既存の README・CLAUDE.md / AGENTS.md・docs/ の主要な文書・CI とデプロイの
設定ファイルを読む。既存 README にしか書かれていない事実（社内の申請手順など）は捨てない。

**リポジトリに無い情報は、ユーザーに一度にまとめて聞く。** 典型は次の6つ。

- 担当者・問い合わせ先（scan のコミット数上位は候補であって答えではない）
- 秘密情報の保管場所（1Password の保管庫名、Vercel の環境変数画面など）
- 外部サービスのアカウントの持ち主と、費用が発生するもの
- 本番・ステージングの URL
- リポジトリの状態（開発中 / 稼働中で保守のみ / 廃止予定）
- 触ってはいけない操作（本番 DB に向く seed、手動デプロイ禁止など）

聞けない実行（自動化・相手が離席）では止まらない。README の末尾に「まだ確認していないこと」の
節を作ってそこに並べる。黙って推測で埋めるのが最悪で、未確認と書いてあれば次の人が埋められる。

## 3. 骨格を組む

`assets/template.md` を出発点にする。上から順に、読者が読む深さに対応している。

1. **冒頭** — 名前、1〜3文の概要、状態・本番 URL・担当、最終確認日
2. **動かす** — 前提、セットアップ、起動、テスト
3. **持つ** — 環境とデプロイ、外部サービスと秘密情報、落とし穴、やってはいけない操作
4. **地図** — docs/ の主要文書、CLAUDE.md への案内、まだ確認していないこと

Web アプリ・API・ライブラリ・CLI・モノレポ・設定置き場で要る節が変わる。種類ごとの差分は
`references/project-types.md`。更新モードでは既存の構成を保つ。

**見出しは慣習名でよい。** README は通読されるより、見出しで引かれる。「セットアップ」
「デプロイ」と書いてあれば読者は迷わず飛べる。結論を見出しに書くのは単発の文書の作法で、
README では探しにくくなる。

## 4. 書く

- **コマンドはコピーしてそのまま通る形で。** 1ブロック1目的。何が起きれば成功かを1行添える
  （「http://localhost:3000 が開けば成功」）。前提の版は `.nvmrc` や `engines` から写す
- **環境変数は「入手先」を書く。** 表は 変数 / 用途 / 入手先 / 必須か。15個を超えるなら
  `.env.example` を正にし、README には入手先と、必須なのに雛形の既定値では動かないものだけ書く
- **外部サービスは表にする。** サービス / 用途 / 管理画面と持ち主 / 秘密情報の置き場所。
  引き継ぎで最も抜けるのがここ
- **落とし穴は 症状 / 原因 / 対処 の3段で。** 読者は症状から引く
- **検証できない主張は書かない。** 「高速」「本番運用可」は、根拠がリポジトリに無ければ削る
- **言語は既存 README に合わせる。** 無ければ日本語
- **地の文は 4,000 字が目安。** 超えたら、その節を docs/ に移して README からリンクする。
  README が長いと、読者は大事な1行（「本番 DB に向けて seed しない」）を読み飛ばす

## 5. 確かめる

3段で確かめる。どれかを飛ばしたら、報告でそう言う。

### 5-1. 機械で検査する

```bash
python3 <このSKILL.mdのあるディレクトリ>/scripts/check_readme.py <README.md> [--repo <リポジトリ>]
```

秘密情報らしき文字列・手元の絶対パス・埋め残し・壊れたリンクとアンカー・存在しない
npm スクリプトと make ターゲット・元ファイルの無い cp・存在しない compose サービス・
実際の origin と違う clone URL は **exit 2**。exit 2 のまま納品しない。
警告（exit 1）は1件ずつ読み、意図どおりなら残してよい。

### 5-2. 手順を実際に通す

セットアップから起動・テストまで、**手元で完結するコマンドは実際に叩く**。依存の導入、
lint、テスト、ビルド、ローカル起動がこれに当たる。書いた手順と実際の手順の差はここでしか出ない。

外部に作用するコマンド（共有 DB へのマイグレーション・seed、デプロイ、課金 API の呼び出し）は
叩かない。叩いていない手順は、報告に「未実行」と書く。「最終確認日」は手順を通した日で、
README を書いた日ではない。

### 5-3. まっさらな読者に読ませる

書き手は文脈を知りすぎていて、欠落が読めない。README **だけ**を渡したサブエージェントに、
引き継ぐ人が最初に抱く質問を答えさせる。手順と質問は `references/cold-reader.md`。
「README からは分からない」と返った質問が欠落で、§2 に戻って埋める。

## 6. 仕上げと報告

- CLAUDE.md / AGENTS.md に同じ手順が書かれていたら、正をどちらにするかユーザーに提案する
  （CLAUDE.md を無断で書き換えない）
- 対外公開する README に限り、`natural-japanese:natural-japanese` を `quick <file>` で呼ぶ。
  社内 README には回さない
- 報告は3点だけ: 確かめたこと（5-1〜5-3 の結果）/ 確かめていないこと（未実行の手順、
  未回答の質問）/ ユーザーに決めてほしいこと

点検モードの指摘は、重い順に「嘘（書いてあるが事実と違う）→ 欠落（無いと作業が止まる）→
古び（コードから導ける一覧・古い日付）→ 体裁」で並べ、各指摘に行番号と根拠のファイルを添える。

## 参照ファイル

- `assets/template.md` — README の骨格。節ごとに何を書くかの注記つき
- `references/project-types.md` — Web アプリ・API・ライブラリ・CLI・モノレポ・設定置き場の差分
- `references/cold-reader.md` — まっさらな読者テストの手順と質問
- `scripts/scan_repo.py` — リポジトリから README の材料を拾う。.env 本体は読まない
- `scripts/check_readme.py` — README の主張をリポジトリと照合する。不適合で exit 2
