# なぜ劣化するのか（原理と実測値）

想定外の荒れ方をしたときの切り分けに使う。以下は実際に測った結果で、推測ではない。

## 劣化要因は重い順に3つ

### 1. フォント欠落 → 文字が □□□ になる（最悪。にじむのではなく消える）

- `matplotlib` の既定フォント（DejaVu Sans）は CJK グリフを持たない。
  日本語を渡すと missing-glyph 警告が出て、全部 □ になる。実測で警告12件。
- `PIL.ImageDraw` の既定フォントも同様。
- `cairosvg` は**太字CJKのフォールバックに失敗する**。同一SVGで `bold入り` が `bold□□`
  になったが、同じSVGを Chromium で描くと正常だった。
- **対策**: レンダリング前にグリフカバレッジを検査する。`build_image.py` はこれを自動でやる。
  単体で確認したいときは fontTools の cmap を見れば良い。

### 2. 解像度不足（deviceScaleFactor=1 / dpi=100 で小さい文字を描く）

12px以下の文字はアンチエイリアスで潰れる。画数の多い漢字（稟、齟齬）は線が繋がる。

| 条件 | OCR一致率 |
|---|---|
| x1 (96dpi) | 94.3% |
| x1.5 | 96.5% |
| x2 | 97.2% |
| x3 | 98.2% |

重要なのは**後から拡大しても回復しない**こと。x1で描いたものを3倍にLANCZOS拡大しても、
ボケたまま画素が増えるだけだった。

ただしこれは**小さい文字の話**。OGPの見出しは40〜110pxあるので、
`deviceScaleFactor=1` で十分鮮明に出る。ここを混同して不要に `--scale 2` を使わないこと。

### 3. 縮小と再圧縮

- x3で描いて1/3に縮小すると8px文字の情報が落ちる（OCR x4→1/4縮小で 97.2%→95.4%）。
- JPEG のクロマサブサンプリングは文字のエッジに色ズレを出す。文字は可逆圧縮（PNG）向き。
- 表示側の縮小は防げない（`presets.md` 参照）。だから**文字を大きくする**しかない。

## SVGを中間形式に挟まない理由

「SVGで合成してからPNGに変換」は一見安全そうだが、実測すると得がない。

- **SVGの `<text>` に自動折り返しが無い。** 可変長タイトルでは改行位置を毎回手計算する必要があり、
  実測では最終行が2文字だけの孤立行になった。HTML/CSSなら `text-wrap:balance` が効く。
- **挟んでも劣化は減らない。** 同一SVGを cairosvg と Chromium で変換した差分は
  ピクセルの0.71%（アンチエイリアスと線幅の差）。つまり「SVG経由だから安全」ではなく
  「変換器次第」。上に書いた太字CJKの地雷も残る。
- **SVGの強み（無限に拡大できる）が発生しない。** 出力寸法は固定なので、
  ラスタライズ回数は HTML→PNG でも SVG→PNG でも1回。中間形式を増やすと地雷が増えるだけ。
- 背景がラスタなので、SVGに入れるには base64 埋め込みが必要になり、ベクタ合成の意味が半減する。

ロゴだけは例外で、SVGで持つべき。任意サイズに無劣化で追従できるのが効く。

## 画像生成モデル（gpt-image系、Nano Banana等）で文字を描かせない理由

これらはラスタライズ工程を持たないので、上記1〜3の劣化は起きない。
代わりに**文字が「間違う」**。レンダリングではなく生成なので、誤字・字形崩れ・文字数違いが混ざる。

文字単位99%の精度でも、20文字のコピーなら `0.99^20 = 81.8%`、
つまり**1文字以上崩れる確率が約18%**。しかも1文字だけ直せず、再生成すると全体が変わる。
社名やサービス名が微妙に違う字になるのが実務では最も痛い。

だから役割を分ける。**背景は生成モデル、文字はブラウザ。**

## 切り分けチェックリスト

文字が汚いとき、上から順に確認する。

1. □ や豆腐が出ている → フォントの問題。`--font` を指定する
2. 文字が切れている・はみ出している → スクリプトが `overflow` を返していないか確認。
   返していれば文字数かレイアウトの問題
3. 全体がぼんやりしている → 出力後にリサイズされていないか。等倍で書き出せているか
4. 文字の周りに色のノイズがある → JPEG/WebPで保存していないか
5. 投稿先で読めない → 作成時の文字サイズ不足。`presets.md` の表示縮小率で逆算する
6. 字形が変・誤字がある → 画像生成モデルが文字を描いている。文字はブラウザ側に移す

## 劣化を数値で確かめる

`scripts/measure_quality.py` に測定器を入れてある。納品前の確認と、
「荒れている気がする」という主観を切り分けるのに使う。

```bash
python3 scripts/measure_quality.py out/ogp.png::ogp out/banner.png::banner
```

**エッジ鋭度** = 一階微分のピーク ÷ その周辺の実コントラスト。
1.00 なら1px以内で立ち上がる理想値、0.50 なら2pxに滲んでいる。校正結果:

| 条件 | 鋭度 |
|---|---|
| 等倍で1回だけラスタライズ（正しい状態） | 0.71 |
| 2400pxで作って1/2に縮小 | 0.68 |
| JPEG q40 に落とす | 0.65 |
| 1200→800→1200 の往復リサイズ | **0.47** |
| 600pxで作って2倍に拡大 | **0.40** |

**0.65未満なら、どこかにリサイズか非可逆圧縮が混入している。**

重要な限界: **この指標は豆腐を検出できない。**
□ は輪郭が綺麗なので鋭度は 0.80 と最高値を示す。
滲み（リサイズ由来）と字形の消失（フォント由来）は別の軸なので、
前者は鋭度、後者はグリフ検査で見る。両方を通して初めて安全と言える。

同時に出る **360px時の字高** は、Slack のリンク展開幅に縮小したときの実効文字サイズ。
日本語は9px未満で判読困難、12px以上で快適。ここが一桁なら、
解像度を上げても解決しないので文字を大きくする。

## デザインツールの画面が綺麗に見える理由

Figma や Illustrator の編集画面で文字が綺麗に見えるのは、ラスタライズされていないからではない。
**画面もラスタライズされている。** 高精細ディスプレイでは物理2倍の解像度で描かれているので
情報量が2倍あり、そのぶん綺麗に見えているだけ。

問題が起きるのは、そこから1倍で書き出したPNGを**同じ画面で見たとき**。
OSが物理ピクセルを埋めるために2倍に拡大するので、そこで初めて滲む。
「キャンバスは綺麗なのに書き出すと汚い」という体感の正体はこれで、書き出し工程の不良ではない。

| 高精細画面で同じ物理サイズで見比べた場合 | 鋭度 |
|---|---|
| 編集画面（2倍解像度で描画） | 0.71 |
| 1倍で書き出したPNG（OSが2倍に拡大） | **0.39** |
| 2倍で書き出したPNG | 0.71（編集画面と同一） |

対処は解像度を上げることで、判断基準は SKILL.md の「解像度が足りているか確認する」にある。
なお等倍ディスプレイで見る場合は1倍書き出しでも 0.69 で、劣化しない。
つまり**必要な解像度は掲載面と閲覧環境で決まる**。常に2倍が正解ではない。

## CJK フォントコレクション（.ttc）のフェイス選択

Noto Sans CJK の .ttc には JP / KR / SC / TC / HK が同梱されている。
面倒なのは、日本語の文字を SC（簡体字）フェイスで描いても**豆腐にはならず、
字形だけが中国語のものになる**こと。骨・者・直・今・令・温 などで形が変わる。
検査を通り抜けるので気づきにくい。

`build_image.py` は .ttc を `@font-face` に丸ごと渡しており、Chromium は
**先頭フェイスを使う**。Noto Sans CJK の .ttc は先頭が JP なので、結果として正しい。
実測でも JP フェイスとの差 10.5、SC との差 35.3 で、JP が選ばれていることを確認した
（`<html lang="ja">` を外しても同じ結果だったので、決めているのは lang ではなくフェイス順）。

ただしこれは Noto の並び順に依存している。**先頭が JP でない .ttc を `--font` に渡すと、
静かに別の字形で描かれる**。自社フォントが .ttc の場合は、単体の .otf/.ttf を切り出して
渡すのが安全。fontTools の `TTCollection` で目的のフェイスを取り出して保存できる。
