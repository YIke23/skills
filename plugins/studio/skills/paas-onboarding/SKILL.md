# paas-onboarding

## 守備範囲

**作るもの**: 対象PaaSを1つ取り上げ、初見のエンジニアがその日のうちに動かせる
単一HTMLのガイド（ELI15水準 = 一般的なWeb開発の知識は前提にしてよいが、
そのPaaS固有の語彙と作法はゼロから説明する）。

**作らないもの**: 複数PaaSの比較検討、既に運用中のサービスのトラブルシュート、
汎用的な技術解説（それは `eli15` の担当）。1ファイル1PaaS。

**範囲はユーザーが決める**。プロンプトに「Hello Worldまで」「本番投入の勘所まで」
「まず概要だけ」とあればそれに従う。指定が無ければ **「Hello Worldが動くまで」** を
既定にして、着手前に一行で宣言する。

## 中核となる考え方

> **UI手順の品質は、独立した2つの軸で決まる。
> 「今日正しいか」（鮮度）は実画面を見ないと分からない。
> 「3か月後も使えるか」（寿命）は形式でしか稼げない。片方だけでは足りない。**

実画面を見れば鮮度は解決する。しかし今日確認したクリック経路も、来月の改修で腐る。
逆にCLIとURLに逃がせば寿命は伸びるが、そのURLが今日生きているかは見ないと分からない。
**だから「実画面で確定させ、腐りにくい形式で書き残す」の両方をやる。**

| 軸 | 効く対策 | 効かない対策 |
|---|---|---|
| 鮮度 | 実画面を読む / スクリーンショット | 形式を変える。役割設定 |
| 寿命 | CLI・URL・ラベル引用に逃がす | 実画面を見る |

## 証拠のレベル

書いてよい情報には出どころの等級がある。**L1を取りに行くのが既定で、
L2で済ませるのは L1 が使えないときだけ。**

| | 出どころ | 分かること | 限界 |
|---|---|---|---|
| **L1** | 実画面（ユーザーのログイン済みブラウザ / スクリーンショット） | 経路・ラベル・URLが確定する。A/Bテストの当たり方も読者と同じ | ログイン済みでないと見えない。初回体験は再現できない |
| **L2** | 公式ドキュメント（当日取得） | ラベルと概念。CLIの正確な文法 | 画面改修に遅れる。スクショはさらに遅れる |
| **L3** | changelog / release notes（当日取得） | 改修があったという事実。L2を疑う根拠 | 手順そのものは分からない |
| ❌ | モデルの記憶 | **何も。使用禁止** | — |

## 鉄の掟

### 掟1: 記憶でUI手順を書かない。例外なし

取得できなかったなら、書かずに「確認できなかった」と書く。
推測で埋めた1階層が、ユーザーの30分を溶かす。

### 掟2: コンソールでは読む以外のことをしない

- **ログインはユーザーが行う。** 資格情報・パスワード・カード番号を入力しない。
  アカウント作成もしない。CAPTCHAも解かない
- 押してよいのは**画面遷移だけ**。作成・削除・保存・送信・同意・課金に関わる操作はしない
- 開く前に「これから何を開くか」を一言伝える
- **キーやトークンが表示される画面では、値を読まない・転記しない。**
  必要なのは「どこにあるか」であって「何であるか」ではない

### 頭に浮かぶ言い訳と、実際に起きること

| 言い訳 | 実際 |
|---|---|
| このPaaSのUIはよく知っている | 知っているのは学習時点のUI。知っているという感覚こそが誤答の原因 |
| APIキーを取るだけの基本操作だ | 基本操作の画面ほどオンボーディング改修の対象になる |
| 検索で出た記事に手順が載っていた | 個人ブログ・Qiita・Zenn・Stack Overflowは日付が古い。**UI手順の出典は公式か実画面のみ** |
| 実画面を見たから経路をそのまま書いてよい | 鮮度は稼げたが寿命は稼げていない。CLI・URLへの逃がしは省略できない |
| ログイン情報をもらえば早い | **禁止。** 早さと引き換えにしてよい種類のものではない |
| ついでにプロジェクトも作っておこう | **禁止。** 読むだけ。副作用のある操作はユーザーの手で |
| 画面にキーが出ているので控えておこう | 会話とHTMLに秘密が残る。検証スクリプトが検出して止める |
| 取得に失敗したが大筋は合っているはず | 大筋が合っていても1階層ズレたら詰まる |

## ワークフロー

### 0. 関門: どのレベルで作れるかを決める

使える手段を順に確認し、**作り始める前にユーザーへ一行で宣言する。**

1. **ブラウザ操作の手段があるか**（Claude in Chrome、Playwright系MCP など）
   → あれば「対象PaaSのコンソールにログインした状態で開いておいてほしい」と依頼する
2. 無ければ **スクリーンショットを依頼できるか**
   → 必要な画面を具体的に挙げて依頼する（「プロジェクト作成後の最初の画面」など）
3. どちらも無理なら **L2で作り、その旨をガイド冒頭に明記する**

**Web取得手段すら無いなら、ガイドを作らずに止まる。** L3すら取れない状態で出力すると、
体裁だけ整った、通常より危険な嘘になる。

### 1. 対象とスコープを確定する

対象PaaSを1つに絞る。ユーザーの目的（何を作っていて何を任せたいのか）を一行で確認する。

### 2. L3 → L2: 骨子を組む

changelogを先に見る。**直近3〜6か月にコンソール改修があれば、L2の記述も疑ってかかる。**
続いて公式docsのQuickstart・料金ページ・CLIリファレンスを取得し、骨子と語彙の対応表を作る。
詳しい探し方は `references/sources.md`。

### 3. L1: 実画面で経路を確定する

**全画面を回らない。** 1画面ごとに往復コストがかかるので、開くのは次に絞る:

- L2で経路が取れなかった画面
- キーの発行画面（読者が最も詰まる。ただし**値は読まない**）
- changelogに改修が載っていた画面
- CLIで代替できない操作の画面

各画面で記録するのは **URL・見出しラベル・そこから次に進む導線** の3点。
読み取りの作法とスクリーンショット依頼の型は `references/console.md`。

### 4. HTMLを書く

規約は `references/html.md`。単一ファイル、外部CDNなし、`color-scheme: light dark`。
手順は必ずこの形にする:

```html
<li class="step"
    data-evidence="console"
    data-source="https://console.example.com/project/_/settings/api"
    data-verified="YYYY-MM-DD">
```

`data-evidence` は `console` / `screenshot` / `docs` のいずれか。
**証拠の等級をHTMLに埋めるので、後から読み手が信頼度を判断できる。**

### 5. 機械検証する

```bash
python3 scripts/check_guide.py <出力.html> \
  --domain <公式ドメイン（カンマ区切り。コンソールのドメインも含める）> \
  --scope overview|hello|production
```

終了コードは 0=問題なし / 1=警告 / 2=不適合。**不適合を残したまま渡さない。**

- 出典・取得日・証拠等級を持たない手順
- 取得日が今日でない手順（＝記憶から書いた疑い）
- 公式ドメイン外・個人記事を出典にしたUI手順
- 直リンクもCLIも無い、クリック経路だけの手順
- **APIキー・トークンらしき文字列の混入**
- 手順ブロック外のUI操作、外部CDN参照、SVGのハードコード色

### 6. 渡す

ファイルを渡し、**どの手順を実画面で確認し、どこがdocs止まりかを口頭でも伝える。**
ガイド冒頭にも同じ内容を書く。読者が信頼度を判断できることが、正確さの次に重要。

## 実画面でも埋まらない穴

**既存アカウントでは、サインアップから初回ウィザードまでが見えない。**
ログイン済みのブラウザで確認できるのは「2回目以降のユーザーが見る画面」であり、
オンボーディングで最も価値のある区間がちょうど死角に入る。

対処は3つ。どれを採ったかをガイドに書く。

1. ユーザーに**新規プロジェクト作成の画面だけスクリーンショットを依頼**する（アカウント作成は不要なことが多い）
2. L2に落とし、**「読者の初回画面はこれと異なる可能性がある」と明記**する
3. その区間を**CLIに置き換える**（多くのPaaSは `init` 系コマンドを持っている）

## 出力の契約

必須セクション（`data-section` で識別。検証スクリプトが存在を確認する）:

| `data-section` | 内容 | 必須 |
|---|---|---|
| `what` | このPaaSが何を肩代わりするのか。自前でやるなら何が要るか | ✅ |
| `vocab` | 語彙の対応表（固有名詞 ↔ 一般概念） | ✅ |
| `pricing` | 無料枠の境界、課金が発生する条件、上限の設定場所 | スコープ次第 |
| `hello` | 最短で動くところまでの手順 | スコープ次第 |
| `keys` | どのキーがクライアントに置いてよく、どれが絶対だめか | ✅ |
| `envsep` | dev/prod の分け方（公式の作法） | スコープ次第 |
| `pitfalls` | 初週に踏む地雷 | スコープ次第 |
| `recovery` | 画面が違ったときの自力復旧（changelog・docs・コンソール内検索） | ✅ |
| `further` | もっと知りたい人へ（一次情報リンク） | ✅ |

`keys` を必須にしているのは、初見のPaaSで最も被害が大きい事故が
「サーバー専用キーをフロントに置く」だからで、これは動いてしまうためテストでは見つからない。

## よくある落とし穴

- **実画面を見たことで安心して、経路をそのまま書かない。** 鮮度と寿命は別の軸。
  L1で確定させた後も、CLIとURLへの逃がしは必ず行う
- **コンソールを回りすぎない。** 全画面を確認すると往復だけで時間が尽きる。
  L2で足りている画面は開かない
- **キーの値を画面から拾わない。** 必要なのは場所であって値ではない。
  スクリーンショットを依頼するときも「キーの部分は隠して構わない」と先に伝える
- **コンソールのURLを自分で組み立てない。** それらしいURLは高確率で404。
  実画面のアドレスバーか、docsに載っているものだけを使う
- **「最新のUIでは」と書かない。** 書いた瞬間に、その文は将来必ず嘘になる。
  「YYYY-MM-DD時点」と日付で書く
- **無料枠を「無料です」で終わらせない。** 寝ている間に増える課金があるかは必ず書く
- **9セクション全部を毎回埋めない。** スコープが「概要だけ」なら手順セクションは要らない

## 参照ファイル

- `references/console.md` — 実画面の読み方、開く画面の絞り込み、スクリーンショット依頼の型、
  秘密情報の扱い、してはいけない操作
- `references/sources.md` — L2/L3の探し方、出典として使ってよい/だめの線引き、
  changelogの見つけ方、取得できなかったときの書き方
- `references/structure.md` — 9セクションそれぞれの中身の作り方、ELI15の水準、
  語彙対応表の作り方、スコープ別の出し入れ
- `references/html.md` — 単一HTMLの規約、`data-*` 属性の契約、フォールバック骨格
  （`eli15` スキルが同じ環境にあるなら、その規約と `assets/base.css` を流用して二重管理しない）
- `scripts/check_guide.py` — 証拠等級・出典・取得日・秘密情報の混入・外部依存を機械的に検査する
