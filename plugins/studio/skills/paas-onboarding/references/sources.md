# 一次情報の取り方（L2 / L3）

このファイルが扱うのは **L2（公式ドキュメント）と L3（changelog）**。
実画面（L1）の読み方は `references/console.md`。

L1が使えるなら、経路とURLはそちらで確定させる。ここで取るのは、
L1では分からないもの（概念、料金の境界、CLIの文法）と、L1を絞り込むための材料
（どの画面が最近改修されたか）。

## 取得の順番

順番に意味がある。**changelogを先に見ると、docsの記述を疑うべきかどうかが分かる。**

### 1. changelog / release notes（最初に見る）

直近3〜6か月にコンソールやダッシュボードの改修が入っていないかを確認する。
入っていたら、学習時点の記憶は全部疑ってかかる。改修が無くても、
「無いことを今日確認した」という事実が後の判断材料になる。

探す場所は概ねこの順:

| パターン | 例 |
|---|---|
| `<公式ドメイン>/changelog` | 最も多い |
| `<公式ドメイン>/blog` の「Launch Week」「Ship」系 | 大きなUI改修はブログ告知が多い |
| docs内の「What's new」「Release notes」 | エンタープライズ寄りのサービスに多い |
| GitHubの Releases | OSSベースのPaaS（CLIのリリースノートも兼ねる） |
| `status.<公式ドメイン>` | 障害情報。今まさに動かない場合の切り分けに使う |

検索クエリは `<サービス名> changelog` `<サービス名> dashboard redesign` あたり。

### 2. 公式ドキュメントの Quickstart / Getting started

手順の主たる出典。`docs.<ドメイン>` か `<ドメイン>/docs` にある。
**言語切り替えがある場合、英語版を正とする。** 各国語版は更新が遅れることが多い。

### 3. 料金ページ

`<ドメイン>/pricing`。見るのは金額ではなく **境界の形**:

- 無料枠を超えたら止まるのか、自動で課金に移るのか
- 何がメーターなのか（実行時間 / リクエスト数 / 転送量 / 行数 / 座席数）
- 使っていなくても増えるものがあるか（常時起動インスタンス、ストレージ、ログ保持）
- 上限やアラートを設定する画面があるか

**「使っていなくても増えるか」は必ず調べる。** 初見で最も怖いのがこれで、
料金ページの表には書かれず、FAQか課金ドキュメントの側にあることが多い。

### 4. 公式CLIのリファレンス（あれば）

CLIに逃がせる手順を洗い出すため。`npm view <pkg> time.modified` や
GitHubのReleasesで最終更新を見ると、生きているCLIかどうかが分かる。
実行環境があるなら `<cli> --version` と `<cli> <subcommand> --help` を
実際に叩くのが最も確実な検証になる。

## 出典の線引き

| 用途 | 使ってよい | 使ってはいけない |
|---|---|---|
| **UI手順・画面ラベル・URL** | 実画面（L1） / 公式docs / 公式blog / 公式changelog | 個人ブログ、Qiita、Zenn、note、Medium、Stack Overflow、YouTube、AIの要約 |
| 料金・制限 | 公式pricing / 公式docs | 比較記事（古い価格が残っている） |
| 概念・設計の考え方 | 公式 + 評判のよい技術記事 | — |
| ハマりどころ | 公式のTroubleshooting + GitHub Issues（日付を見る） | 日付不明の記事 |

検証スクリプトは個人記事ドメインを `data-source` に指定した時点で不適合にする。
概念の理解に読むのは自由だが、**出典として名前を出せるのは公式だけ**。

## 公式ドメインの見分け方

検索結果の上位が公式とは限らない。ドキュメントの正体を確かめる手掛かり:

- サービス本体のドメインと同一か、そのサブドメイン（`docs.` `developers.` `developer.`）
- 公式サイトのフッター/ヘッダーからリンクが張られている
- 買収・改称の履歴がある場合、旧ドメインがリダイレクトしているか（していないなら情報も古い）

紛らわしい第三者ドキュメント（`<サービス名>-docs.com` のような）に当たったら、
公式サイトのナビゲーションから辿り直す。

## 直リンクURLの扱い

- **自分で組み立てない。** それらしいURLは高確率で404。docsに書かれているものだけを使う
- プレースホルダ（`/project/_/settings/api` の `_` など）は、公式がその書き方をしている場合のみ使う
- URLが取れなかったら、経路を書く代わりに **「コンソール内の検索窓で〈ラベル〉を検索」** に逃がす。
  多くのコンソールはコマンドパレットや検索を持っていて、これは改修に強い

## docsとUIが食い違っているとき

**実画面（L1）が見られるなら、実画面が勝つ。** 以下はL1が使えない場合の話。

公式docsも遅れる。スクリーンショットは本文よりさらに遅れる。

1. スクショと本文が違う → **本文（ラベル名）を採る**
2. どちらも怪しい → 経路を書かず、URLとラベルと「見つからなければ検索」だけにする
3. changelogに該当する改修があった → **その事実をガイドに書く**
   （「YYYY-MM にこの画面は再構成されている。古い記事の経路は当たらない」）

3番は地味に効く。読者が古い記事を見つけてしまったときの判断材料になる。

## 取得できなかったとき

推測で埋めない。ガイドの該当箇所にこう書く:

> この手順は今回、一次情報を確認できなかった。公式の Quickstart（URL）を開いて、
> 「〈ラベル〉」を探すところから始めてほしい。

**空白は不便だが、誤った経路は有害。** 不便と有害は交換してはいけない。
