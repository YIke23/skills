# ガイドの構成

## 水準（ELI15）

読者は **Web開発はできるが、そのPaaSは初見のエンジニア**。

- 説明しない: HTTP、環境変数、npm、git、REST、JSON、SQLの基本
- 必ず説明する: そのPaaS固有の名詞、そのPaaSが前提にしている作法、
  他社と同じ名前で違う意味の概念
- 一文は短く。比喩は1セクションに1つまで。**比喩で埋めるとELI5になり、
  エンジニアには情報密度が足りない読み物になる**

判断に迷ったら「これは公式docsを読めば分かるか？」ではなく
**「初見でこれを知らないと詰まるか？」** で選ぶ。ガイドの価値はdocsの要約ではなく、
docsが前提にしている暗黙知を先に渡すことにある。

## セクション別の作り方

### `what` — 何を肩代わりするのか（必須）

3〜5文。**自前でやるなら何が必要かとの対比で書く。** 対比があると
「なぜ料金を払うのか」「どこまで任せているのか」が同時に伝わる。

避けるべきは公式のキャッチコピーの言い換え。「モダンで高速なプラットフォーム」は
何も伝えていない。「PostgreSQLの管理・認証・ファイル保存・APIの自動生成を
まとめて引き受ける。自前なら DB運用 + 認証実装 + S3 + APIサーバー」の形にする。

### `vocab` — 語彙の対応表（必須）

**このガイドで最も価値のあるセクション。** 表で書く。

| このPaaSでの呼び名 | 一般的な概念 | 注意 |
|---|---|---|

初見で詰まる原因の大半は機能ではなく語彙。Project / Environment / Deployment /
Instance / Organization / Service は各社で意味がズレる。特に危険なのは
**他社と同じ名前で違う意味を持つもの**で、読者は既知だと思って読み飛ばす。
その行には注意を書く。

階層構造（Organization > Project > Environment のような入れ子）があるなら、
それも図か短い箇条書きで示す。課金とアクセス権がどの階層に付くかは必ず書く。

### `pricing` — 無料枠と課金（スコープ次第）

書くこと:
- 無料枠の境界と、超えたときの挙動（停止するのか課金に移るのか）
- メーターの単位
- **使っていなくても増えるもの**（常時起動、ストレージ、ログ保持、座席）
- 上限・アラートの設定場所（あれば手順、無ければ「無い」と書く）

「無料です」で終わらせない。読者が知りたいのは金額ではなく **事故の形**。

### `hello` — 最短で動くまで（スコープ次第）

手順は `<li class="step">` で書き、CLI > 直リンクURL > ラベル引用の順に逃がす。
理想は **10手順以内**。それを超えるなら、前提（アカウント作成など）を
別セクションに追い出せないか見直す。

各手順に必ず含めるもの:
- `data-source`（公式URL）と `data-verified`（今日の日付）
- 何が起きたら成功なのか（「〜と表示されれば成功」）

「成功の判定」を書かない手順は、詰まったときに読者が前に進めない。

### `keys` — キーの取り扱い（必須）

**必須にしている理由**: サーバー専用キーをフロントに置いても動いてしまうので、
テストでは見つからない。見つかるのは漏洩したときだけ。

表で書く:

| キーの名前 | 置いてよい場所 | 漏れると何ができるか |
|---|---|---|

「公開してよい」キーがある場合、**なぜ公開してよいのか**（何が権限を守っているのか）を
一行で説明する。仕組みを知らないと、読者は「じゃあ全部公開でいいのでは」に流れる。

ローテーション方法と、漏らしたときの初動も1〜2行で。

### `envsep` — 環境の分け方（スコープ次第）

そのPaaSが公式に想定している分け方を書く（別プロジェクトを立てるのか、
1プロジェクト内のenvironmentなのか）。**公式の作法から外れると、
後から移行するのが最も高くつく部分。** 無料枠との兼ね合いも触れる。

### `pitfalls` — 初週の地雷（スコープ次第）

3〜6個。出典は公式のTroubleshooting、changelogの破壊的変更、
GitHub Issuesの頻出（日付を確認する）。
**「よくある質問」の言い換えにしない。** 読者が自力では予測できないものを選ぶ。

### `recovery` — 画面が違ったとき（必須）

このガイド自体が古びることを前提にしたセクション。ここだけは
UI操作の記述を手順ブロックの外に書いてよい（検証スクリプトも除外している）。

- コンソール内の検索/コマンドパレットの使い方
- changelogのURL（改修があったかを読者自身が確認できるように）
- 公式docsのQuickstartのURL
- 公式のサポート窓口・コミュニティ

### `further` — もっと知りたい人へ（必須）

一次情報へのリンクを3〜6本。各行に「何が書いてあるか」を一言添える。
リンクの羅列だけでは、どれを開くべきか読者が判断できない。

## スコープ別の出し入れ

| ユーザーの指定 | `--scope` | 含めるセクション |
|---|---|---|
| 「まず概要だけ」「どういうものか知りたい」 | `overview` | what / vocab / pricing / keys / recovery / further |
| 指定なし、「使ってみたい」「始め方」 | `hello` | + hello |
| 「本番で使いたい」「導入したい」 | `production` | + envsep / pitfalls |

**埋めることを目的にしない。** スコープ外のセクションを薄く足すと、
密度が落ちて全体の信頼性が下がる。
