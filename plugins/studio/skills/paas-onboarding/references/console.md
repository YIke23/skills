# 実画面から手順を起こす

## 前提

**ログインはユーザーが行う。** こちらは資格情報を入力しない。アカウントも作らない。
できるのは、ユーザーがログイン済みにしたブラウザを読むことだけ。
この線は「早いから」「本人の許可があるから」で越えない。

開始時の依頼文の型:

> 対象のコンソールにログインした状態で開いておいてください。こちらは画面を読むだけで、
> 作成・削除・保存の操作はしません。キーが表示される画面は、値を伏せてもらって構いません。

## 開く画面を絞る

1画面ごとに往復コストがかかる。**全画面を回ると、ガイドを書く前に時間が尽きる。**
開くのは次の4種類だけ:

| 開く | 理由 |
|---|---|
| L2（docs）で経路が取れなかった画面 | ここが本来の目的 |
| キーの発行・表示画面 | 読者が最も詰まる。ただし**値は読まない** |
| changelogに改修が載っていた画面 | docsが追いついていない可能性が高い |
| CLIで代替できない操作の画面 | 逃がし先が無いので実画面が要る |

逆に、docsのQuickstartに経路とURLが揃っていて、changelogにも改修が無い画面は開かない。

## 各画面で記録する3点

1. **URL**（アドレスバーの実物。組み立てない）
2. **見出しラベル**（画面上の文字列をそのまま。「」で囲んで引用として書く）
3. **次に進む導線**（次の手順へどう繋がるか）

スクリーンショットより、**ページのテキストやアクセシビリティツリーを読む方が正確**。
ラベルの表記揺れ（全角/半角、大文字小文字）まで取れる。
レイアウトの理解が必要なときだけ画像を併用する。

## してはいけない操作

- 作成・削除・保存・送信・公開・招待
- 設定の変更、プランの変更、支払い方法の登録
- 同意ダイアログやCookieバナーの承諾
- OAuth連携の承認
- フォームへの入力と送信

**押してよいのは画面遷移だけ。** 副作用のある操作が必要な手順は、
「ここでユーザーが〈操作〉する」と書いて、実行はユーザーに委ねる。
実行しないまま次の画面を見たい場合は、ユーザーに進めてもらってから読む。

## 秘密情報の扱い

キーの発行画面は、その性質上、画面に秘密そのものが出ている。

- **値を読まない。転記しない。要約もしない。** 必要なのは「どこにあるか」だけ
- スクリーンショットを依頼するときは、先に「キーの部分は塗りつぶして構いません」と伝える
- 誤って会話に入ってしまったら、その旨を伝え、**ローテーションを勧める**
- 生成したHTMLに `sk_live_` や JWT らしき文字列が入っていないか、
  `check_guide.py` が検査して不適合にする

ガイドに書くのは、値ではなくこの3つ:

> どの画面にあるか / どれが公開してよくどれが駄目か / 漏らしたときにどう無効化するか

## 既存アカウントでは見えないもの

ログイン済みのブラウザで見えるのは「2回目以降のユーザーの画面」であり、
**オンボーディングで最も価値のある区間 — サインアップから初回ウィザード — が死角に入る。**

多くのPaaSでは、新規プロジェクト作成の画面までは既存アカウントでも再現できる。
そこまでは実画面で取り、アカウント作成そのものはL2に落とす。

穴を埋める手段は3つ。**どれを採ったかをガイド本文に明記する。**

1. 新規プロジェクト作成の画面だけスクリーンショットを依頼する
2. L2に落とし、「読者の初回画面はこれと異なる可能性がある」と書く
3. その区間をCLI（`init` 系コマンド）に置き換える

3が使えるなら3が最善。初回ウィザードはUIの中で最も改修が激しい部分なので、
実画面で確定させても寿命が短い。

## スクリーンショット依頼の型

ブラウザ操作の手段が無い場合。**欲しい画面を具体的に指定する。**
「コンソールの画像をください」では、必要な画面が来ない。

> 次の画面のスクリーンショットをもらえますか。
> 1. プロジェクトを選んだ直後のトップ画面（左のメニュー全体が入るように）
> 2. APIキーが表示されるページ（キーの値は塗りつぶして構いません）
> それぞれ、ブラウザのアドレスバーが写っていると助かります。

**アドレスバーを頼むのを忘れない。** URLは経路より寿命が長く、
ガイドの中で最も価値のある一行になる。

## 実画面を見た手順の書き方

実画面で確定させても、**クリック経路をそのまま書いてはいけない。**
鮮度は稼げたが寿命は稼げていないため。確定したURLとラベルを使って、
腐りにくい形に書き直す。

```html
<li class="step"
    data-evidence="console"
    data-source="https://console.example.com/project/_/settings/api"
    data-verified="2026-08-30">
  <a href="https://console.example.com/project/_/settings/api">APIキーのページ</a> を開く。
  「Project API keys」という見出しの下に2種類のキーが並んでいれば正しい画面。
</li>
```

`data-evidence` の値:

| 値 | 意味 |
|---|---|
| `console` | 実画面をこちらで読んで確定させた |
| `screenshot` | ユーザーから受け取った画像で確定させた |
| `docs` | 公式ドキュメントのみ。実画面は未確認 |

`docs` が混じること自体は問題ない。**混じっていることを隠すのが問題。**
ガイド冒頭に、どこまで実画面で確認したかを一文で書く。
