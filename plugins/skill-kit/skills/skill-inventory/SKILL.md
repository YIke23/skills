# skill-inventory

いま自分のセッションに何が生えていて、それが GitHub 上の正からどれだけずれているかを1枚にする。

出力は2つ。**ターミナルには要対応の差分だけ**を短く出し、**全一覧は HTML アーティファクト**として
publish してリンクを渡す。60行を超える表をターミナルに流すと、肝心の「どれが古いのか」が
スクロールで流れて消える。

**このスキルは読み取り専用。** `git fetch` 以外は何も書かないし、`plugin update` も
`marketplace update` も実行しない。更新コマンドは提示するが、打つのはユーザー。
プラグインの更新はセッションの再起動を伴い、走らせた瞬間にいまの状態が失われるので、
「今どれだけ遅れているか」を見せることと更新することは同じ手で混ぜない。

## なぜ手で数えられないのか

スキルの出自は**3系統ある**。同時にロードされるのに、置き場所も版の形式も更新経路も違う。

| 系統 | 実体 | 版の形式 | 更新する人 |
|---|---|---|---|
| 組み込み | 本体バイナリの中（SKILL.md はディスクに無い） | 本体のバージョン | 本体の更新 |
| CLI のプラグイン | `~/.claude/plugins/cache/<mp>/<plugin>/<sha>/` | **git SHA** | `plugin update` |
| デスクトップのプラグイン | `local-agent-mode-sessions/<A>/<B>/rpm/plugin_*/` | semver | アプリ |
| デスクトップのスキル | `local-agent-mode-sessions/skills-plugin/<B>/<A>/` | — | claude.ai の設定 |
| ユーザー / プロジェクト | `~/.claude/skills/`、`<repo>/.claude/skills/` | 無し | 手 |

`claude plugin list` は上の表の**2行目しか返さない**。デスクトップ側は
`installed_plugins.json` に載らないので、CLI だけを見ると `anthropic-skills:*` や
`design:*` が丸ごと消える。逆に `ls ~/.claude/skills` はプラグイン由来を1件も含まない。

さらに、GitHub との差分を出す公式手段が無い。`marketplace update` は更新してしまうので、
「今どれだけ遅れているか」はその瞬間に消える。だから差分は marketplace の git クローンに
対して自前で計算する。

背景と、実測で確認した7つの罠は `references/systems.md` に書いた。**出力の読み方に迷ったとき、
差分の状態値の意味を確認したいとき、集計結果が直感と合わないときは必ずそれを読むこと。**

## 手順

### Step 1 — 収集する

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/collect_inventory.py \
  --cwd "$(pwd)" -o /tmp/skill-inventory.json
```

標準ライブラリだけで動く。marketplace ごとに `git fetch` するので数秒かかる。
オフラインや、ネットワークに出したくないときは `--no-fetch` を付ける
（その場合 ahead/behind は最後に fetch した時点の値になるので、出力にそう書く）。

stderr に要約が1行出る。JSON の各キーの意味は `references/systems.md` の「出力の読み方」。

### Step 2 — 組み込みスキルを補う

**JSON は組み込みスキルを列挙しない。** 本体バイナリに埋まっていてディスクに SKILL.md が
無いからで、`builtin_skills.enumerable` が `false` なのは「無い」ではなく
「ここでは分からない」の意味。

ここは**自分のセッションで見えている一覧が正**。システムプロンプトのスキル一覧のうち、
名前空間が付かず、かつ `~/.claude/skills` にも `<repo>/.claude/skills` にも実体が無いものが
組み込み。それを一覧に足す。版は `host.claude_code_version` に追随するので、
差分の列は「—（本体に追随）」にする。

判別に迷ったら、素の名前で候補に出るのは組み込みとユーザー/プロジェクトスキルだけで、
プラグイン由来は必ず `<plugin>:<skill>` の形になる、という規則を使う。

### Step 3 — 差分を読む

`totals` の3つの数が要対応の件数。それぞれ原因が別なので、混ぜずに見る。

| 数 | 意味 | 見る場所 |
|---|---|---|
| `marketplaces_behind` | marketplace のクローンが GitHub より遅れている | `marketplaces[].behind` |
| `plugins_behind` | 導入済みプラグインが marketplace の HEAD より古い | `plugins[].drift` |
| `loose_diverged` | 手元のスキルコピーが GitHub 側と構成が違う | `loose_skill_drift[]` |

**この3つは独立に起こる。** marketplace が GitHub と同期していても導入済みは古いままでいられる
（`marketplace update` は `installed_plugins.json` を書き換えないため）。3つ全部が
`0` でないと「同期している」とは言えない。

状態値ごとに何を勧めるかは決まっている。**コマンドは提示するだけで、実行しない。**

| 状態 | 意味 | 提示するもの |
|---|---|---|
| marketplace `behind: N` | クローンが GitHub より N コミット遅れ | `plugin marketplace update <名前>` |
| plugin `behind` で `changed_paths` あり | 配っているスキルのファイルが実際に変わっている | `plugin update <plugin>@<mp>` と、その後の再起動 |
| plugin `behind` で `changed_paths` 空 | 遅れてはいるが中身は同じ | 急ぎではない、と明記して優先度を下げる |
| plugin `unrelated` | 導入済みの SHA がクローンに無い | 改名や URL 変更の後始末。`marketplace remove` → `add` → `install` の入れ直し |
| loose `diverged` | 手元のコピーと GitHub 側でファイル構成か中身が違う | **GitHub 側が正。** 手元が古いか壊れている（下記） |
| loose `untracked` | 同名がどの marketplace にも無い | 作業中。異常として挙げない（下記） |
| `not-comparable` | 手元に git クローンが無い系統 | 比較できないことを明示する。空欄にすると「同期済み」に見える |

**GitHub が正。** `~/.claude/skills/` と `~/dev/skills` には作ったばかりのスキルが
一時的に入るが、それは開発の途中経過であって正ではない。だから `diverged` は
「どちらを正にしますか」と聞き返さない。手元が古いか壊れていると読み、
GitHub 側で置き換える前提で報告する。

- `missing_files` があるなら、手元のコピーが不完全。参照ファイルやスクリプトが
  欠けたまま動いているので、そのスキルは途中で失敗する。取り直しが要る
- `differing_files` だけでも同じ。手元の編集が未 push なら push が要るという話であって、
  手元を正に切り替える話ではない

例外は `untracked` — **GitHub に同名が無い**スキルだけ。これは移す前の作業中なので、
要対応に挙げず「手元のみ、比較対象なし」と書く。`diverged`（同名が GitHub にある）と
`untracked`（無い）で扱いが逆になる点に注意する。

`disable-model-invocation: true` のスキルは件数に入れない（`totals.manual_only` で別枠）。
ディスクにはあるが**モデルからは呼べない**ので、呼べる件数に混ぜると水増しになる。
行は残して「手動のみ」と印を付ける。

### Step 4 — 重複ロードを見る

`duplicate_names` は、同じ名前のスキルが複数系統から同時に生えている状態。
2種類あって、深刻さが違う。

- **名前空間が違う**（`git-flow:git-commit` と `studio:git-commit`）
  → どちらを呼ぶか選べるが、意図せず別物を呼ぶ余地が残る
- **名前空間まで同じ**（CLI とデスクトップに同名のプラグインが入っている）
  → **どちらが呼ばれるか名前から判別できない。** これは一覧を出すこと自体が価値になる箇所で、
    `origin` と `path` を並べて、同じ名前が2つの実体を指していることを見せる

`shadowed_plugins` は、プラグインとして配られているのに手元のコピーが使われているスキル。
試作用に `~/.claude/skills/` へ置いたものをリポジトリへ移した後、手元を消し忘れると起きる。
名前空間が付かないのでふつうのユーザースキルに見えるが、実体は GitHub から取り残された古い枝。

### Step 5 — アーティファクトを作る

**先に `artifact-design` スキルを読む。** その後で HTML を書く。

ページの構成はこの順にする。理由は、開いた人が最初に知りたいのは「何か対応が要るか」で、
全一覧はその後の確認だから。

1. **要対応** — 差分がある行だけ。1件も無ければ「差分なし」と明示する。
   空のセクションを出さずに黙って省くと、検査したことが伝わらない
2. **サマリー** — 系統別の件数、marketplace の同期状態、収集時刻、`--no-fetch` なら その旨
3. **全一覧** — 下の列。ソートと絞り込みが効くようにする
4. **収集できなかったもの** — `notes` の内容、組み込みを列挙できない理由、
   `not-comparable` の系統。**ここを省かない。** 見えていない範囲を書かないと、
   一覧が全数だと誤読される

全一覧の列。

| 列 | 中身 | 注意 |
|---|---|---|
| 呼び出し名 | `invocable_as` | 素の名前か名前空間付きかが出自の手掛かりになるので、加工しない |
| 種別 | `kind`（skill / command） | |
| 出自 | `origin` | 組み込み / CLI プラグイン / デスクトップ / ユーザー のように日本語で |
| プラグイン | `plugin` | ユーザー・プロジェクト・組み込みは「—」 |
| 版 | `version` | `version_kind` が `git-sha` なら先頭7桁に丸める。semver はそのまま |
| 差分 | `drift_state` | 色分けする。`not-comparable` を「同期済み」と同じ見た目にしない |
| 説明 | `description_short` | 全文は `description`。折りたたむか、行の展開で見せる |

色は3値に寄せる。**要対応（behind / diverged / unrelated）/ 問題なし（current / in-sync）/
判定不能（not-comparable / untracked / pending）** の3つ。判定不能を問題なしと同じ色にすると、
比較していない範囲が同期済みに見える。ここが一覧の一番の落とし穴。

publish したらリンクを渡し、**ターミナルには要対応の行だけを短く出す。**
差分が1件も無ければ、系統別の件数と「差分なし」の1行で終わらせる。

## 判断をユーザーに残す

このスキルは状態を見せるところまでで終わる。特に次の3つは、正解が状況で変わるので
勝手に決めない。

- **プラグインを更新するか。** 更新は再起動を伴うので、いま何かの作業の途中なら後回しが正しい
- **重複をどう解消するか。** 名前空間が同じ重複はプラグイン構成の問題で、
  一覧の外で決める話になる
