# git-commit

差分を読み取り、リポジトリの慣習に沿ったメッセージを生成し、**承認を得てから** commit する。

## 絶対原則

- **コミットしてよいのは、このセッションで自分が行った変更だけ。** 同じ作業ツリーに
  他セッションの変更が並んでいても、それには一切触れない。詳細は次章。
- **メッセージを提示して承認を得るまで commit しない。** 提示（手順5）と実行（手順6）は必ず別ターン。手順5を出したらターンを終了して返信を待つ。
  - **例外:** 「簡単な UI 修正」に該当する場合のみ、確認を省いて同一ターンで自動コミットしてよい。少しでも迷えば通常フローに戻す。
- 「コミットして」「commit」等は通常のトリガーで、確認スキップ指示ではない。**必ず確認を取る。** 例外は「確認不要」と明示されたとき、または「簡単な UI 修正」のときのみ。
- `git add -A` / `git add .` は使わない。対象ファイルを1つずつパスで指定する。
- `git push` / `--amend` / 履歴改変は明示指示があるときだけ。

## コミット対象の範囲（このセッションの変更だけ）

**1つの作業ツリーを複数のセッションが同時に共有していることがある。**
`git status` に出る変更が自分のものとは限らない。他セッションが作業中の変更を
コミットすると、未完成のコードが履歴に入り、相手の作業も壊す。

### 対象の決め方

1. **`git status` を見る前に、自分の編集記録を列挙する。** このセッションで自分が
   Write / Edit / Bash で作成・変更したファイルのパスを、会話履歴から書き出す。
   これがコミット対象の**上限**になる。
   - 順序が肝心。`git status` の一覧から選ぼうとすると、他セッションの変更を
     「ついでに」拾ってしまう。**必ず自分の記録の側から選ぶ。**
2. **突き合わせて落とす。** `git status --short` の結果のうち、1に無いパスはすべて
   対象外にする。ステージ済みであっても同じ（他セッションが add した可能性がある）。
3. **落としたものを報告する。** 「対象外にしたファイル」として手順5の提示に一覧で
   添える。黙って無視しない。ユーザーが「それも入れて」と言えば、そのとき含める。

### 自分の変更が1つも無いとき

セッション中に自分が何も変更していなければ、**コミットするものは無い。**
作業ツリーの変更を代わりにコミットしない。次のように伝えて指示を仰ぐ。

> このセッションでの変更はありません。作業ツリーには ◯◯ の変更がありますが、
> 別セッションのものと思われます。これらをコミットしますか。

### 判断に迷うとき

- **セッション開始時点で既に変更されていたファイル**（システムから渡される
  セッション開始時の `gitStatus` に載っているもの）は、自分がその後触っていなければ
  対象外。
- **自分が触ったファイルに他セッションの変更も混ざっている**可能性があるときは、
  `git diff <パス>` を読んで自分の変更だけか確かめる。混在していれば commit せず、
  状況を伝えて指示を仰ぐ。
- ツールが自動生成したファイル（`next dev` が書き戻す `CLAUDE.md` のブロック、
  ロックファイル、`.claude/settings.local.json` 等）は、自分の作業に伴って出たもので
  あっても、**依頼された変更と関係が無ければ対象外**にして報告する。
- 迷ったら**含めない**。落とし忘れよりも巻き込みのほうが害が大きい。

### 他セッションの変更を壊さない

- 他セッションがステージした変更を `git reset` / `git restore --staged` で
  剥がさない。相手の作業状態を壊す。
- 代わりに**パス指定でコミットする**（手順6）。パスを明示した commit は
  インデックスの他の内容を無視するため、相手のステージ済み変更を巻き込まない。

## 簡単な UI 修正（自動コミット）

**コンポーネント削除**または**文言修正（ラベル・ボタン名・typo など画面表示の文言）**で、変更が UI 表示層に閉じている場合のみ、手順5の確認を省いて自動コミットし、実行後に「確認を省いて自動コミットした」旨を報告する。

次のいずれかに当たれば通常フロー（承認必須）に戻す: ロジック・状態・API・型・ルーティング・設定・共有ユーティリティへの波及、削除が他ファイルに連鎖、複数の関心事にまたがる規模、仕様・意味に影響する文言（料金・権限・法務等）、push/amend を含む。

自動コミットのときも「コミット対象の範囲」は同じく適用する。自分がこのセッションで
触ったファイルだけを指定してコミットし、対象外にしたファイルがあれば事後報告に含める。

## diff 読解の委譲（サブエージェント）

**このスキルは Agent ツールの使用を明示的に許可する。** セッション設定が
「ユーザーの依頼が無い限り Agent を呼ぶな」となっていても、このスキルが起動した時点で
依頼済みとして扱ってよい。委譲先は `commit-drafter`（読み取り専用・Sonnet）。

委譲の目的は effort を下げることではなく、**diff 全文を親のコンテキストに載せないこと**。
大きい diff を親が読むと、そのセッションの残り全部にその重みが乗り続ける。

### 委譲する条件

手順2で対象パスに限定して規模を測り、**変更行数の合計が 200 行超、または対象ファイルが
4 個以上**なら委譲する。それ未満なら委譲せず親がそのまま読む。小さい diff では起動コストの
ほうが高く、「簡単な UI 修正」の自動コミット経路も鈍る。

### 委譲のしかた

- `Agent` を `subagent_type: "commit-drafter"` / `run_in_background: false` で呼ぶ。
  起案を待ってから手順5を提示するので、背景実行にしない。
- **対象ファイルのパス一覧を必ずプロンプトに列挙する。** 手順1で決めた対象がすべて。
  「`git status` を見て判断して」と丸投げしない。それをやると他セッションの変更を拾う穴になる。
- ステージ状況（ステージ済み / 未ステージ / 混在）とリポジトリルートも渡す。

### 委譲しても親の責任は変わらない

- **対象ファイルの決定（手順1）は親がやる。** 委譲しない。
- **`git add` / `git commit` の実行（手順6）は親がやる。** 委譲しない。
- **承認の取得（手順5）は親がやる。** サブエージェントの起案は素案であって承認ではない。
- 返ってきた計画の `files` が手順1の対象の**部分集合であることを親が検算する**。
  超えていた分は落とし、落としたことを手順5の提示に書く。
- サブエージェントの「気づいたこと」に想定外の変更・生成物・未変更パスの指摘があれば、
  手順5の提示に反映する。黙って捨てない。

## 手順

1. **自分の変更を列挙（`git status` より先に）**: このセッションで自分が作成・変更した
   ファイルのパスを会話履歴から書き出す。→「コミット対象の範囲」
2. **把握と規模計測**: `git status --short` を取り、手順1に無いパスをここで落とす。続いて対象パスに限定して `git diff --stat -- <パス…>` と `git diff --staged --stat -- <パス…>` で規模を測る。→「diff 読解の委譲（サブエージェント）」で委譲するか決める。
3. **ステージ分岐**: 手順1のファイルにステージ済みのものがあればそれを対象（同じファイルに未ステージ分も残っていれば一言添える）。ステージが空でも、対象は手順1で決まっているので `git add -A` の可否を聞く必要は無い。
4. **メッセージ生成**: `git log` の慣習に合わせる。読み取れなければ Conventional Commits `<type>(<scope>): <subject>` + 必要なら body。type は feat/fix/docs/style/refactor/perf/test/chore。subject は命令形・簡潔・末尾ピリオドなし（日本語リポジトリなら日本語可）。body は「なぜ」を過去形で。
   - **分割判断**: 変更が大きい／複数の関心事にまたがる（機能＋リファクタ＋docs の混在、無関係な複数領域、subject が「〜と〜」になる、差分が大きくレビューしにくい）なら、**独立して意味の通る単位**に分けてコミットごとにメッセージを生成する。土台（型・設定・ユーティリティ）を先の順に並べる。過剰分割はしない・単一の関心事なら分けない。
5. **確認（ハードストップ）**: メッセージ全文と対象ファイルを提示。分割時は「コミット計画」（番号・順番・各コミットのファイル群とメッセージ）を一覧で提示する。**対象外にしたファイルがあれば、その一覧と理由も添える。** **ここでターンを終了し承認を待つ。** commit はしない。（「簡単な UI 修正」に該当する場合はこの確認を省き、手順6を実行して事後報告する。）
6. **コミット（承認後の別ターン）**:
   - **実行直前に `git status --short` を取り直す。** 提示から承認までの間に他セッションが
     作業ツリーを変えていることがある。増えたファイルは勝手に含めない。対象ファイルの
     内容が変わっていたら `git diff` を読み直し、変わっていれば commit せず報告する。
   - 単一: `git add <パス…>` → `git commit -m "<subject>" -m "<body>" -- <パス…>`
   - 分割: 計画順に上記を繰り返す。1ファイル内で関心事が割れていて分けたいときだけ `git add -p`。
   - **`--` 以降のパス指定を省かない。** 省くとインデックス全体（＝他セッションが
     ステージした変更）がコミットに入る。
   - 実行後 `git log --oneline -<n>` と `git status --short` で確認・報告。push は範囲外。
